# FinDocQA 模块可靠性测试框架与 C3-B 落地计划

日期：2026-07-28  
状态：方法论基线；2026-07-29 已落第一批 C3-B ReliabilityProfile / Decision Table / 有界组合样板，待 Evaluator 复评
当前样板模块：`C3-B Formula Context Recovery`

---

## 1. 为什么要专门建立这套测试框架

当前 C3 的问题已经很明确：

```text
不是“公式 100 × 80% 会不会算错”
而是“系统拿来计算的公式、变量、表格、脚注、跨页证据，到底是不是正确、完整、唯一且属于当前公式”
```

最近连续出现的 False Pass 都属于同一类问题：

```text
限制变量虽然出现在 min/max 中，但并没有真正约束最终结果

普通邻块写了“见下页”
→ 公式错误继承跨页权限
→ 从下一页补出缺失变量

公式明确依赖 footnote
→ 当前不支持
→ 却被静默忽略

同一个 formula_id 对应多个 CanonicalFormula
→ 歧义被误当成“没有元数据”
→ 继续 PASS
```

如果继续采用：

```text
发现 1 个反例
→ 修 1 个
→ 再发现 1 个
→ 再修 1 个
```

测试会长期停留在“追 Bug”阶段。

下一步应该升级成：

> **先定义系统不可违反的规则，再系统性生成输入组合去攻击这些规则。**

也就是说，从“案例驱动测试”升级为“规格 / 不变量驱动的可靠性测试”。

---

## 2. 总体方法论

建议 FinDocQA 后续所有高风险确定性模块统一采用下面的测试体系：

```text
Specification / Safety Contract
        ↓
Invariant Testing
        ↓
Decision Table / Input-Space Modeling
        ↓
Combinatorial Testing
        ↓
Property-Based Testing
        ↓
Metamorphic Testing
        ↓
Mutation Testing
        ↓
Regression Corpus
        ↓
Module Reliability Gate
```

这些方法不是互相替代，而是各自解决不同问题。

| 方法 | 主要解决的问题 | C3-B 中的作用 |
|---|---|---|
| Specification / Invariant | 什么叫“绝对不能错” | 定义 False PASS 禁止规则 |
| Decision Table | 输入状态有哪些 | 公式/表格/脚注/跨页/lineage 状态建模 |
| Combinatorial Testing | 组合太多测不完 | 2-way / 3-way 覆盖状态交互 |
| Property-Based Testing | 人工案例想不全 | 自动生成 CanonicalDocument / metadata 组合 |
| Metamorphic Testing | 正确答案难直接定义 | 加无关证据后结果必须保持不变 |
| Mutation Testing | 测试本身是否真的有效 | 故意破坏 Gate，测试必须报错 |
| Regression Corpus | 历史 Bug 不复发 | 永久保留已发现 False Pass |

## 3. 第一层：先定义 Invariant，而不是先写 case

C3-B 第一版建议先确定以下 Safety Invariants。

### I1｜歧义不可执行

```text
只要关键证据存在无法消除的多候选歧义
→ ready_for_execution 必须 False
```

包括但不限于：

```text
2+ CanonicalFormula
2+ linked table candidate
2+ continuation candidate
冲突 metadata
无法唯一确定的 formula / table / footnote binding
```

### I2｜未解析显式依赖不可 PASS

```text
linked table / footnote / continuation 等依赖被明确声明
但当前无法解析
→ 不得 PASS
```

### I3｜跨文档不得自动拼接

```text
Recovery 只允许同一 CanonicalDocument
→ 跨文档 continuation / table / formula evidence 自动拒绝
```

### I4｜物理相邻不是结构关联

```text
同页
相邻 block
相邻页
变量名相同
数值看起来能用

都不能单独产生 binding
```

必须依赖显式结构关系或当前已批准的保守恢复规则。

### I5｜ready_for_execution 是强合同

```text
ready_for_execution=True
必须同时满足：

Formula Gate PASS
+ 必需变量绑定完整
+ 无 unresolved dependency
+ 无 ambiguity
+ source lineage 完整
+ 无 cross-document recovery
```

### I6｜Recovery 不能绕过 Gate

永远保持：

```text
Recovery
→ LocalContextVariableBinder
→ FormulaEvidenceGate
→ PASS / REVIEW / FAIL
```

Recovery 自己不能直接宣布“证据足够”。

### I7｜无关证据不能改变结果

```text
增加 unlinked table / unrelated page / unrelated document
→ 当前公式的 recovery / gate 结果不应发生变化
```

这条后面用于 Metamorphic Testing。

## 4. 第二层：建立 C3-B Input-Space Model

以后不再从“我能想到什么 case”出发，而是先列状态维度。

第一版建议至少包含：

| Factor | Values |
|---|---|
| formula_count | 0 / 1 / 2+ |
| formula_identity | unique / duplicate / missing |
| table_count | 0 / 1 / 2+ |
| table_linkage | none / explicit / conflicting |
| footnote | none / explicit-supported / explicit-unsupported |
| continuation_count | 0 / 1 / 2+ |
| continuation_linkage | none / explicit / conflicting |
| marker_source | none / anchor / neighbor / conflicting |
| page_relation | same-page / ±1 / cross-document |
| lineage | complete / missing / conflicting |
| variable_binding | complete / missing / ambiguous |
| metadata_source | block / canonical-formula / both-conflict |

简单理解：

```text
以前：
“我再想一个奇怪例子。”

以后：
“这个模块一共有哪几个维度？每个维度有哪些状态？”
```

这样未知问题会逐步转化成可枚举的状态空间。

---

## 5. 第三层：Combinatorial Testing

如果每个 Factor 都有 3 个状态，12 个 Factor 全量组合是：

```text
3^12 = 531441
```

不适合人工穷举。

因此采用 covering array / t-way 思路：

```text
2-way
→ 任意两个 Factor 的状态组合都至少出现一次

3-way
→ 任意三个 Factor 的状态组合都至少出现一次
```

C3-B 建议：

```text
基础功能：2-way
安全关键组合：3-way
```

尤其优先覆盖：

```text
formula_identity × footnote × lineage
formula_identity × continuation × page_relation
table_linkage × variable_binding × lineage
marker_source × continuation_linkage × page_relation
metadata_source × formula_identity × dependency_type
```

目的不是测完所有 50 万组合，而是系统覆盖“因素之间的交互”。

---

## 6. 第四层：Property-Based Testing

组合测试负责决定“哪些状态组合要覆盖”。

Property-Based Testing 负责在这些状态下自动生成大量具体数据。

例如自动生成：

```text
CanonicalDocument
CanonicalPage
CanonicalBlock
CanonicalFormula
CanonicalTable
SourceLineage
FormulaEvidence
metadata
```

随机变化：

```text
formula_id
block_id
table_id
page
reading_order
linked refs
continuation refs
lineage 是否缺失
metadata 是否重复
变量名 / 数值
```

测试不再要求知道每一个具体算式的最终数字，而是检查不变量：

```python
if canonical_formula_count >= 2:
    assert result.ready_for_execution is False

if unsupported_dependency:
    assert result.status != PASS

if cross_document_recovery:
    assert result.ready_for_execution is False
```

### Property-Based Testing 最重要的价值

人工测试：

```text
人负责想输入
```

Property-Based Testing：

```text
人负责定义正确规律
机器负责大量寻找反例
```

这正是当前 C3-B 最需要的能力。

## 7. 第五层：Metamorphic Testing

对于金融长文档 QA，很多场景很难直接为每个复杂输入提供精确 Oracle。

但我们往往知道：

> 做某种“无关变化”以后，系统结果不应该改变。

### MR1｜增加无关表格

```text
原：formula → linked table t1

新增：
unlinked table t99
expense = 999999

期望：
Recovery / Gate 结果不变
```

### MR2｜增加无关文档

```text
新增 doc99
ratio = 5%

期望：
当前 formula 不得受到影响
```

### MR3｜修改未关联证据中的数值

```text
unlinked table:
100 → 999999999

期望：
结果完全不变
```

### MR4｜调整无关 block 的顺序

只要没有影响显式 linkage：

```text
当前公式绑定结果不应变化
```

### MR5｜增加无关跨页 marker

```text
neighbor block 新增“见下页”
```

如果该 marker 不属于 formula anchor：

```text
不得产生 adjacent-page recovery
```

Metamorphic Testing 很适合发现“系统偷偷依赖了不该依赖的证据”。

---

## 8. 第六层：Mutation Testing

仅看到：

```text
763 tests PASS
```

并不能证明测试质量高。

需要反过来测试“测试本身”。

例如故意把：

```python
if canonical_formula_count > 1:
    return REVIEW
```

变异成：

```python
if canonical_formula_count > 1:
    return PASS
```

然后重新运行测试。

正确结果必须是：

```text
测试立即失败
```

如果故意把安全逻辑改坏以后：

```text
全部测试仍然 PASS
```

说明测试集有盲区。

### C3-B 第一批 Mutation 点

建议至少包含：

```text
删除 ambiguity REVIEW
删除 cross-document reject
删除 lineage check
删除 unsupported footnote REVIEW
允许 neighbor marker 授权跨页
允许 unlinked table 自动加入
绕过 FormulaEvidenceGate
```

最终关注：

```text
Mutation Score
= 被测试成功发现的 mutation / 总 mutation
```

## 9. 第七层：Regression Corpus

我们目前已经发现的 bug 不应该丢掉。

这些历史问题以后成为固定 canary：

```text
R-C3-001
min(expense, limit * 2)
不能证明 <= limit

R-C3-002
neighbor “见下页”不能授权 formula 跨页

R-C3-003
formula-level unsupported footnote 必须 REVIEW

R-C3-004
2+ CanonicalFormula 不能退化成 metadata missing

R-C3-005
unlinked table 不得补变量

R-C3-006
cross-document continuation 必须拒绝
```

原则：

```text
历史 Bug
→ 固定 Regression Corpus
→ 永不删除
```

但 Regression Corpus 只是最后一道保险，不再承担“发现所有未知问题”的主要责任。

## 10. C3-B Safety Matrix V1

建议下一阶段先实现这张核心矩阵。

### 10.1 Candidate cardinality

| 对象 | 0 | 1 | 2+ |
|---|---|---|---|
| CanonicalFormula | 可按 block/evidence 信息继续 | UNIQUE | REVIEW |
| Explicit Table Candidate | 依赖存在则 REVIEW | UNIQUE | REVIEW |
| Continuation Candidate | 依赖存在则 REVIEW | UNIQUE | REVIEW |
| Required Variable | REVIEW | UNIQUE | REVIEW |
| Required Lineage | REVIEW | PASS | REVIEW/FAIL |

### 10.2 Relationship

| 关系 | 默认处理 |
|---|---|
| explicit linkage | 允许继续验证 |
| same-page only | 不足以绑定 |
| adjacent-block only | 不足以绑定 |
| adjacent-page only | 不足以绑定 |
| same variable name | 不足以绑定 |
| semantic similarity | C3-B 当前不使用 |
| cross-document | 禁止自动恢复 |

### 10.3 Dependency

| Dependency | 状态 |
|---|---|
| supported + resolved | 可继续 |
| supported + ambiguous | REVIEW |
| explicit + unsupported | REVIEW |
| explicit + missing | REVIEW |
| no dependency | 可继续其他 Gate |

## 12. Module Reliability Gate

以后模块是否允许进入下一阶段，不应该只看 pytest 数量。

建议逐步形成：

```text
Regression Tests             PASS
Invariant Tests              PASS
2-way / 3-way Coverage       PASS
Property-Based Tests         PASS
Metamorphic Relations        PASS
Mutation Testing             PASS
False PASS                   0
API                          0（离线模块）
```

其中 C3 最高优先级指标：

> **False PASS = 0**

因为对于确定性金融计算：

```text
“不知道 / REVIEW”
通常比
“非常精确地给出错误答案”
更安全。
```

## 13. 这套框架以后不只服务 C3

C3-B 只是第一个样板模块。

后续可以复用到：

```text
C3-C Semantic Variable Binder
→ 主体 / 指标 / 时间 / 单位绑定歧义

Document Scope Resolver
→ 文档候选唯一性、错误跨文档

Retrieval
→ 无关文档注入、顺序扰动、候选污染

Reranker
→ 排名稳定性、无关候选干扰

Evidence Binding
→ claim ↔ evidence 错绑

Verification
→ False PASS / False Reject

Submission / Output Contract
→ 状态组合、字段完整性、fail closed
```

最终形成 FinDocQA 公共能力：

```text
每新增一个模块
↓
先写 Specification / Invariant
↓
再做正常功能
↓
再通过 Reliability Gate
↓
最后才能接入主链
```

## 14. 明天建议怎么开始

不要一上来就写很多测试代码。

建议严格按下面顺序：

### Step 1｜冻结 C3-B Safety Contract

先确认 10～20 条 Invariant。

重点问题：

```text
什么情况下必须 PASS？
什么情况下必须 REVIEW？
什么情况下必须 FAIL？
什么情况下永远不能 ready_for_execution=True？
```

### Step 2｜冻结 Input-Space Model

确认：

```text
有哪些 Factor
每个 Factor 有哪些状态
哪些状态组合属于非法输入
哪些状态组合必须 fail closed
```

### Step 3｜先做 Decision Table Oracle

建立一个与生产实现解耦的小型 Reference Model：

```text
输入状态
→ expected PASS / REVIEW / FAIL
```

不要复制生产代码实现。

### Step 4｜做 2-way / 3-way 组合生成

先从 C3-B 最关键的 6～8 个 Factor 做起。

### Step 5｜接 Property-Based Testing

自动生成 CanonicalDocument / FormulaEvidence。

重点攻击 Invariant，而不是验证固定答案。

### Step 6｜增加 Metamorphic Relations

优先：

```text
加无关表格
加无关页面
加无关文档
改无关数值
加 neighbor marker
```

### Step 7｜最后做 Mutation Testing

验证：

```text
我们建立的这些测试
到底能不能真的打死错误实现
```

## 16. 一句话原则

以后不要再用：

> “我暂时没有想到新的反例，所以这个模块应该可靠。”

而应该用：

> **“我们先定义什么叫正确，再让机器系统性组合、随机生成、扰动和故意破坏实现，持续寻找违反这些规则的输入。”**

这套思路应作为 FinDocQA 后续高风险模块的通用可靠性测试方法。
