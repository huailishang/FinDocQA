# B-03 下一代检索路线实验设计

## 1. 为什么先设计再执行

H-35 已证明：`canonical_lexical=3/15`、现有 `lexical_hybrid=1/15`、修正 BM25=`3/15`，两个候选对 12 个 baseline miss 都恢复 `0/12`。下一步候选包括 semantic retrieval(语义检索)、query planning(查询规划)、Know-where(知道去哪里找)，但三条路线成熟度和基础设施成本并不一样。

项目现状：

```text
semantic retrieval
→ 已有 CanonicalEmbeddingIndex / EmbeddingEvidenceRetriever 接口
→ 缺的是本轮可用的真实 embedding model(向量模型)与授权/环境确认

query planning
→ 已有 QueryPlanBuilder
→ 已能输出 metric/year/numeric/relation/section/negative 等可审计检索信号

Know-where
→ 有完整设计方向
→ 有 Canonical section_path / heading / table 等结构底座
→ 但没有现成 DocumentMemory / section_tree / navigate_structure / explore_document 主链实现
```

因此 H-36 不能让 Executor 临时发明三套实现。Evaluator 先冻结三条路线的“最小可比较实现”，Executor 再执行同基线横评。

## 2. 参考依据

本设计吸收项目已有材料：

- `docs/reference/Knowhere与LLM-Wiki借鉴分析.md`
  - Knowhere-like Document Memory(类似 Knowhere 的文档记忆)定位为 Parser 后的结构导航层；
  - P-KW1 的最小目标是 heading/section tree + table/figure/source binding，再与平面检索同基线比较。
- `docs/reference/KDDCup2026冠军方案对FinDocQA吸收分析.md`
  - Knowhere = “地图”；Champion Runtime(冠军运行时) = “这次怎么找”；
  - 先探查真实结构，再根据观测继续导航；
  - TopK 应逐步从“最终候选”降级为 Active Working Set(活动工作集)。
- `docs/reference/对比计划.md`
  - D3-02 查询词增强、D3-04 结构感知检索本来就是当前检索链的明确缺口。
- `docs/modular-architecture.md`
  - M7 的目标接口已经定义为 `page / section / block retrieval`，并允许 embedding / structure-aware retriever 替换。

代码底座：

```text
src/retrieval/embedding_index.py
→ page-level semantic retrieval 接口

src/retrieval/query_plan.py
→ deterministic query planning(确定性查询规划)

src/document/contracts.py
→ CanonicalPage.section_paths
→ CanonicalBlock.section_path / heading_level / table_id / reading_order

src/structure/blocks.py
→ Section / ParsedDocument

src/structure/chunks.py
→ StructureChunk / parent_context / atomic table boundary
```

结论：Know-where 不是从零开始，但当前只有“结构数据合同”，没有“导航运行时”。H-36 只能做 **Know-where Lite / P-KW1 structure-navigation probe(结构导航探针)**，不能假装已经实现完整 Know-where/Agent Runtime。

## 3. 统一实验问题

统一冻结 H-35 的：

```text
15 QA / 4 docs
same parsed roots
same candidate document scope
same authoritative evidence pages
same Top5 metric
canonical_lexical baseline = 3/15
baseline hits = 00941 / 01858 / 00476
baseline misses = 12
```

统一晋级门：

```text
preserve 3/3 baseline hits
AND recover >=4/12 baseline misses
AND regress 0 baseline hits
```

三条路线只回答“哪类机制值得进入产品 shadow experiment(影子实验)”，本轮禁止融合。


## 3.1 本轮路线裁剪

2026-08-18 经进一步评估，本轮 H-36 暂停 semantic retrieval(语义检索)，只执行 query planning(查询规划) 与 Know-where Lite(轻量知道去哪里找)。

原因：semantic 路线虽然已有接口，也可能已有环境中的 embedding API(向量 API)，但真正公平执行前还需要：

```text
4 份文档 page-level embedding
→ 冻结 embedding model / dimensions / input normalization
→ 建立并冻结 page vector index
→ 控制批次 / 成本 / API 调用
→ 再做 query embedding + cosine Top5
```

这已经是一个独立的向量检索基础设施实验，不适合塞进当前以“查询规划 vs 结构导航”为核心的 H-36。

因此：

```text
H-36 当前：Query Planning + Know-where Lite
Semantic Retrieval：DEFERRED_CANDIDATE(延期候选)
```

如果前两条都不能产生通用改善，再单独决定是否值得启动 semantic retrieval 实验。

## 4. Deferred｜semantic retrieval(语义检索)

### 4.1 后续要验证什么

测试：当问题与官方证据页的字面词不一致时，语义向量是否能够直接把正确 page 拉入 Top5。

### 4.2 后续候选实现

复用项目现有：

```text
CanonicalEmbeddingIndex
EmbeddingEvidenceRetriever
canonical_page_embedding_text
```

固定：

```text
retrieval unit = canonical page
query = visible question text + visible options
candidate docs = H-35 frozen candidate scope
page text = canonical_page_embedding_text(page)
rank = cosine similarity
Top5 = highest five pages
```

不得同时增加：

```text
query rewrite
HyDE
BM25 fusion
reranker
QueryPlanBuilder
section routing
Gold-derived terms
```

### 4.3 本轮状态

本轮不执行，不做 embedding capability discovery(向量能力发现)，不构建向量索引，不调用 API。未来单独启动时再冻结：

```text
如果已有真实本地 embedding model
→ 执行 Lane A

如果只有 SiliconFlow/其他外部 API
→ Lane A = BLOCKED_BY_AUTHORIZATION
→ 不得调用，不得伪造向量
```

SiliconFlow 现有 adapter 只能说明接口已经存在，不等于本轮已授权调用。

## 5. Lane A｜query planning(查询规划)

### 5.1 要验证什么

测试：问题不是“词搜不到”，而是“直接把题面全部词扔进去，查询表达不够好”时，结构化 Query Plan 是否能改善 page ranking。

### 5.2 冻结实现

复用项目现有 `QueryPlanBuilder`，不改词表。

Only principal change(唯一主变量)：

```text
canonical _evidence_terms(question)
→ QueryPlanBuilder.window_retrieval_terms
```

QueryPlan 已有：

```text
metric
numeric
year
section/title hint
negative/exception
relation
question terms
option terms
classification hint
```

最终页面打分仍使用 H-35 canonical lexical 同一 scorer family(打分器家族)，同一 Top5。

这样测到的收益才能归因于：

> **“先把题目整理成更好的检索表达”**

而不是同时换掉 Retriever。

### 5.3 明确禁止

```text
根据 15 题结果增加新 alias
修改 metric lexicon
修改 section hints
修改 relation lexicon
人工删词/加词
semantic embedding
reranker
```

## 6. Lane B｜Know-where Lite / P-KW1

### 6.1 Know-where 本轮到底是什么

不是完整 Knowhere，也不是 LLM Agent。

冻结定义：

> **先把当前 Canonical Document 变成一个最小可导航结构视图；先在“目录/章节/表格位置”层找方向，再进入页面正文检索。**

它测试的是 hierarchy/navigation(层级导航)本身是否有用。

### 6.2 最小 Document Memory Lite(轻量文档记忆)

不重跑 Parser，不建设 Graph，不改 `src/**`。由 task-local runner 从现有 Canonical Document 派生：

```text
DocumentMemoryLite
├─ document_id
├─ nodes[]
│  ├─ node_id
│  ├─ node_type = section / table / page
│  ├─ title_or_path
│  ├─ page_start
│  ├─ page_end
│  ├─ parent
│  ├─ previous / next
│  ├─ table_ids
│  └─ source lineage
└─ page_to_section_path
```

只允许使用现成字段：

```text
CanonicalPage.page_number
CanonicalPage.section_paths
CanonicalBlock.section_path
CanonicalBlock.heading_level
CanonicalBlock.reading_order
CanonicalBlock.table_id
CanonicalTable.caption / headers
```

不得人工为 FinanceBench qid 编目录规则。

### 6.3 导航链冻结成两阶段

```text
Question
↓
Stage 1 Structure Probe(结构探查)
用 baseline canonical evidence terms 对：
section path / heading / table caption / headers
做通用结构匹配
↓
得到 Top structure nodes + page ranges
↓
Stage 2 Local Evidence Search(局部证据搜索)
仅在 admitted page ranges 中
使用原 canonical lexical page scorer
↓
Top5 pages
```

这里**故意不使用 QueryPlanBuilder**，避免和 Lane B 混变量；也不用 embedding，避免和 Lane A 混变量。

### 6.4 Soft navigation(软导航)而不是硬裁剪

吸收 KDD Cup 的 Soft Working Set(软工作集)思想：结构探查不能一次判断错就永久删掉整份文档。

本轮最小规则：

```text
primary admitted pages
= selected structure nodes 覆盖页
+ 每个 selected range 前后 1 页 neighbor

若 primary admitted pages < 5
→ 按 structure score 顺序继续扩下一个 node
直到至少 5 页
```

本轮不做“根据答案证据充分性动态重开全局空间”，因为那会引入 Verifier/Agent Runtime，超出单变量结构导航实验。真正的 `P-DA1 Soft Evidence Workspace → P-DA2 Explore Before Solve` 放在 Know-where Lite 有收益之后。

### 6.5 必须保存导航轨迹

每题至少记录：

```text
probe_terms
structure_nodes_seen
selected_nodes
selected_reason
selected_page_ranges
neighbor_expansion
admitted_pages
final_top5_pages
```

这样 Evaluator 可以判断：

```text
是结构导航选错方向
还是方向选对但局部 page scorer 排错
```

## 7. 两条执行路线如何保证公平

| Lane | 唯一核心机制 | 不允许混入 |
|---|---|---|
| Query Planning | 改 query representation | embedding / structure routing / scorer 改造 |
| Know-where Lite | section/table hierarchy navigation | QueryPlan / embedding / LLM / HyDE |

公共不变量：

```text
15 cases
4 docs
parsed roots
candidate document scope
Gold attribution
Top5 cutoff
baseline hit controls
```

## 8. 大包内部执行顺序

虽然是一个大包，但不是三个人随便并行开发，而是：

```text
Phase 0 Evaluator Design Freeze
→ 本文档，已完成

Phase 1 Executor Preflight
→ 验证两条 Lane 的输入/依赖/可执行性
→ 特别确认 semantic 是否有本地真实 embedding model
→ 验证 4 份文档的 section/table metadata 足够构建 DocumentMemoryLite

Phase 2 Three-Lane Measurement
→ A / B / C 各自隔离运行
→ 不根据中间结果修改其他 Lane

Phase 3 Executor L2
→ scope / Gold isolation / hash / deterministic replay / qualification

Phase 4 Evaluator L3
→ 独立复跑
→ 选择下一产品候选，或重新评估更高层架构
```

若 Phase 1 发现 Know-where Lite 的结构元数据不足，不允许临时重写 Parser；Lane C 应明确 `BLOCKED_BY_STRUCTURE_SUPPLY`，这本身说明瓶颈落到了 document structure(文档结构)供给层。

## 9. 本轮不做什么

明确排除：

```text
完整 Knowhere 服务栈
知识图谱
LLM Wiki
LLM plan-agent
动态多轮 Agent
semantic + query-plan + Know-where 融合
reranker
HyDE
Parser 重做
为了 15 题增加特例
```

本轮先解决一个更基础的问题：

> **FinDocQA 当前下一步应优先增强“查询表达”，还是“文档结构导航”？如果两条都不够，再单独启动语义向量路线。**

只有路线选择有证据后，再进入产品主链设计。
