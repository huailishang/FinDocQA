# FinDocQA 本地评测标准

## 1. 目标

在没有比赛排行榜反馈时，用一套固定、可复现、可人工审计的本地评测体系判断改动是否真正提升系统，而不是依赖“感觉答案更好”。

评测原则：

> 固定题集 + 固定金标 + 分阶段指标 + 错误簇复核 + 版本对比。

比赛原项目和历史题目不删除，继续保留在私有历史仓库中；FinDocQA Public 仓库只保留评测框架、脱敏示例和不受比赛数据授权限制的公开样例。

## 2. Gold Set 怎么来

### 2.1 第一阶段：从现有高置信题目建立种子集

优先选取已经经过多次人工核对、证据明确、答案争议小的题目，而不是随机抽题。

建议初始规模 50～100 题，覆盖五个领域：

- 金融合同
- 财务报告
- 保险条款
- 监管文件
- 研究报告

同时覆盖主要题型：

- 单文档事实题
- 多选/逐选项判断
- 数值计算
- 表格取数
- 跨文档比较
- 排序/筛选
- 否定、条件、例外
- 时间/版本约束
- 多跳证据

### 2.2 历史提交如何作为候选证据

历史排行榜只用于**筛选 Gold 候选**，不能直接替代原始文档真值。

建议按可归因强度分级：

```text
S 级：单题提交，且除了答案字段外其他字段完全不变；分数方向明确
A 级：小批量提交，且仅答案字段变化；总增益与改动题数高度一致
B 级：小批量提交有净增益，但无法确认每一道题分别贡献多少
C 级：仅来自最终高分版本、模型共识或人工直觉，没有独立反事实验证
N 级：单题错误改动导致明确降分，可作为负向对照候选
```

使用规则：

- `S/N` 级优先进入第一轮人工核验；
- `A` 级逐题回到原文确认后才可升级；
- `B/C` 级只进入候选池，不因为“最终版本分数高”就直接当 Gold；
- 所有等级最终都必须满足“原始文档证据闭环”才能成为正式 Gold。

特别注意：如果一次提交同时改变了答案、Token、reasoning、模型输出或其他评分相关字段，就不能把分数变化简单归因于答案修改。

### 2.3 第一版 30 题怎么选

不要直接从“所有涨分题”里取前 30。第一版建议采用三类混合：

```text
12～15 题  历史强反事实锚点（S/N 级优先）
8～10 题   高难度代表题（计算、跨文档、条件/例外、表格、时序）
5～8 题    未被历史提交反复优化过的覆盖题
```

同时满足下面的覆盖约束：

- 五个金融领域都必须出现，任一领域不能少于 3 题；
- 至少覆盖事实、多选、计算、表格、跨文档、排序/比较、否定/例外、时序等主要类型；
- 难度不要全部集中在“过去已经修好的题”；
- 至少 20% 题目不应由历史排行榜直接提供答案方向，防止评测集变成比赛经验回放；
- 第一版 30 题中保留约 20% 作为 Shadow，日常开发不针对它调规则。

更稳妥的流程是先建立 40～50 道候选池，经人工核验和覆盖检查后再冻结最终 30 道，而不是先规定 30 个 qid 再强行证明它们正确。

### 2.4 每道题必须保存的金标

每题至少包含：

```text
case_id
question
domain
question_type
gold_answer
required_documents
gold_evidence_pages
gold_evidence_snippets
critical_claims
calculation_or_reasoning_notes
annotation_status
annotation_source
```

其中最重要的不是只有 `gold_answer`，而是同时保留：

```text
答案是什么
+ 为什么
+ 来自哪份文档
+ 哪一页/哪一段
+ 哪些 Claim 必须成立
```

这样才能判断错误到底发生在文档召回、证据定位、推理、计算还是最终输出。

## 3. 怎么判断 Gold Set 本身合理

一道题只有满足下面条件，才进入正式 Gold Set：

1. **答案可由原始文档独立推出**，不能依赖排行榜分数或模型多数票。
2. **证据可定位**到明确文档、页码和局部文本/表格。
3. **题意边界明确**，不存在多个同样合理的解释；有争议的题进入 `disputed` 集，不计主分。
4. **至少两次独立复核**。重要或复杂题建议两个人/两轮独立标注后再仲裁。
5. **模型不可见金标**。运行时不能把答案、required_documents 或 gold evidence 泄露给待测链路。
6. **题目具有代表性**，不能全部是容易题，也不能全部来自某一个错误簇。

正式状态建议：

```text
DRAFT
→ REVIEWED
→ GOLD
→ DISPUTED / RETIRED
```

只有 `GOLD` 题进入主评分。

## 4. 不再只看一个“总正确率”

FinDocQA 应分层评分。

### 4.1 文档范围

衡量是否先找对文档：

- Required Document Recall@1 / @3 / @5
- 多文档题 Complete Recall@K
- 错召回文档数量

### 4.2 证据定位

衡量找对文档后是否定位到正确位置：

- Evidence Page Recall@K
- Evidence Hit Rate
- 必要 Claim 的证据覆盖率
- 无证据/错页/错表比例

### 4.3 最终答案

按题型分别计算：

- 单选/多选：Exact Match、集合 Precision / Recall / F1
- 数值：精确匹配或规定容差内正确率
- 文本：规范化 Exact Match + 人工语义复核
- 排序/列表：顺序正确率、集合完整率

### 4.4 Claim 与验证

衡量“答案对，但理由是否真的站得住”：

- Claim SUPPORT / REFUTE / UNRESOLVED 准确率
- Claim Evidence Binding 准确率
- 错误证据放行率（应尽量低）
- 正确答案被错误 Gate 阻断率

### 4.5 工程指标

同时记录：

- Prompt Token
- Completion Token
- 总 Token
- 模型调用次数
- Recovery 次数
- Provider/格式失败数
- 单题耗时

质量上升但 Token 或恢复次数暴涨，也不能直接视为有效优化。

## 5. 推荐的主评分方式

第一阶段不要设计过度复杂的综合分，先保留四个核心面板：

```text
A. Answer Accuracy
B. Document/Evidence Recall
C. Verification Reliability
D. Cost / Stability
```

任何代码改动至少满足：

```text
主目标指标提升
且
核心回归题不显著下降
且
错误证据放行率不恶化
且
成本增长在可接受范围
```

正式晋级建议采用“硬门槛 + 指标提升”，而不是简单加权总分。

例如：

```text
答案准确率不得下降
关键 Gold Case 不得新增错误
Evidence Recall 不得明显下降
错误证据放行率不得上升
满足以上条件后，再比较目标能力指标是否改善
```

## 6. 数据集分层

不要让所有题都承担同一个职责。

建议分成：

```text
Gold-Core
  40～60题
  每次修改必跑，稳定回归

Gold-Hard
  20～40题
  复杂计算、多文档、条件/例外等高难题

Failure-Regression
  持续增加
  每修复一个真实 bug，就加入对应回归案例

Shadow
  不参与日常调参
  用于防止对 Gold-Core 过拟合
```

最重要的是 `Shadow`：开发时不能反复根据它调规则，只在阶段性版本时运行。

## 7. 比赛历史题怎么处理

原 AFAC 项目先不删除。

它的作用改成：

```text
历史错误库
+ 已知高置信案例来源
+ 将来官方/高分答案公布后的校准来源
```

但不要把比赛排行榜答案直接当 Gold Truth。

如果未来官方公布标准答案或可靠高分解答：

```text
官方/公开答案
→ 回到原文逐题核验
→ 补齐证据页和 Claim
→ REVIEWED
→ GOLD
```

也就是说，排行榜可以提供“线索”，原始文档证据才是最终金标来源。

## 8. 建议的第一版实施顺序

```text
Step 1  从现有题目挑 30 个最确定案例
Step 2  给每题补答案 + 文档 + 页码 + 关键证据 + Claim
Step 3  做两轮独立人工复核
Step 4  写统一 benchmark runner
Step 5  输出 Answer / Retrieval / Evidence / Verification / Cost 五类指标
Step 6  再扩到 50～100 题
Step 7  留出 20% Shadow，不参与日常调参
```

第一版宁可只有 30 道真正可靠的题，也不要为了凑 100 道把有争议的题塞进金标。
