## 1. 赛题题目类型分析

A 组 100 道题看似都是"读文档选答案"，实际按解题方法可以分成几类。理解这些类型，才能明白为什么"搜索到片段直接回答"远远不够。

### 1.1 公式计算题

题目给出具体数值，要求从条款中提取计算公式后代入计算。

**示例：金融合同多选题（退保金排序）**

> 平安智盈金生累计所交保费 10 万元，保单账户累计收益 2 万元，在第 7 个保单年度末退保；国寿增益宝个人账户价值 12 万元，在第 7 个保单年度末退保（退保费用 0%）；平安富鸿金生现金价值 9 万元。则三者退保所得金额从高到低排序为？

需要从 3 份保险条款中分别找到退保金的计算公式：

- 平安智盈金生：第 6-10 年现金价值 = 累计保费 + 收益 × 75% → 10 + 2 × 0.75 = 11.5 万
- 国寿增益宝：退保费用 0%，退保金 = 个人账户价值 = 12 万
- 平安富鸿金生：现金价值直接给出 = 9 万
- 排序：12 > 11.5 > 9 → 选项 A 正确

这类题的难点是**公式分散在不同文档**，必须逐份定位条款，提取参数，再做算术。只搜"退保"两个字得到的片段大概率漏掉"第 6-10 年"这个关键条件。

**示例：金融合同多选题（多保险联合赔付计算）** 涉及 3 份医疗险条款，每份赔付规则不同：有的先扣免赔额再按比例赔，有的 0 免赔全额赔，还要看费用是否属于保险责任。

### 1.2 跨文档对比题

题目明确要求对比两份或多份文档中的数据或条款。

**示例：金融合同多选题（比亚迪连续两年年报对比）** 需要分别从 2024 年报和 2025 年报中提取营业收入、净利润、经营现金流、研发投入等数据，再逐项对比增长/下滑关系。单看任意一份年报都不够。

**示例：金融合同多选题（跨公司财务指标对比）** 需要同时打开比亚迪和美的两份年报，提取同一类指标做横向比较。如果检索模块只返回了比亚迪的数据，美的的数据没召回，答案就直接错一半。

### 1.3 多文档联合推理题

题目涉及多个产品/法规/条款，需要把各文档的信息拼起来做综合判断。

**示例：金融合同多选题（四产品身故保险金排序）** 涉及 4 份保险条款，每份的身故保险金计算公式都不一样：有的是"已交保费 vs 现金价值取大"，有的是"已交保费 × 比例 + 账户价值"，有的是"基本保额 × 系数"。必须四份条款都读到、都算对，才能排序。

**示例：金融合同多选题（多产品免责范围判断）** 4 个选项分别来自 4 份不同条款，每个选项都要到对应条款里找"责任免除"章节。这本质上是 **4 次独立的条款定位任务**，拼在一起成了一道多选题。

### 1.4 条款定位题

题目问的是某一条款的具体规定，答案就在文档的某个章节里。

**示例：金融合同多选题（等待期内出险处理）** 4 个选项涉及 4 份不同保险，每份的"等待期"条款可能都有例外规定（比如"因意外伤害发生上述情形的，无等待期"）。需要逐份定位等待期条款，再判断该选项情形是否适用例外。

### 1.5 事实查找题

题目问的是文档中直接记载的事实，不需要计算，只需要定位。

**示例：金融合同多选题（行业数据查找）** 这类题在研报中通常有明确的数字和结论，但研报动辄几万字，数字散落在不同段落。如果检索只返回了前半部分，可能恰好漏掉了"2022 年"这个限定词。

### 小结

这五种类型不是互斥的。比如 金融合同多选题 既是多文档联合推理（3 份条款），又是公式计算。金融合同多选题 既是跨文档对比，又是事实查找。

一个有效的系统至少要解决两个问题：

1. **如何确保所有相关文档都被读到**（跨文档题不能只读一篇）
2. **如何在文档中精确定位关键信息**（计算题要找到公式，条款题要找到对应章节）

硬截断策略对第 1 个问题无能为力，对第 2 个问题取决于关键信息是否恰好在前 4000 字内。

### 1.6 什么是 RAG（检索增强生成）

RAG（Retrieval-Augmented Generation）的核心思想：在让模型回答之前，先从文档中把相关内容找出来，只把最相关的片段交给模型。标准流程分三步：

1. **索引（Indexing）**：把文档切成小块（chunk），用 Embedding 模型编码成向量，存入向量数据库
2. **检索（Retrieval）**：把问题编码成向量，搜索最相似的 top K 个文本块
3. **生成（Generation）**：把检索到的文本块和原始问题拼成 prompt，交给 LLM 生成答案

金融长文本问答本质上就是一个 RAG 任务。本方案的硬截断等于跳过了"检索"这一步。后续优化的核心，就是逐步补齐 RAG 的各个环节。

## 2. PDF 解析方案

RAG 系统的质量上限由两个因素决定：检索策略和文档解析质量。

### 2.1 为什么 PDF 解析是第一步且最重要

整个 pipeline 的链路是：`PDF → 解析 → 文本 → 切片 → 检索 → LLM 回答`。如果第一步就把表格变成了乱码、公式丢失了、段落顺序乱了，后面所有环节都在错误的文本上工作。

保险条款和财报类 PDF 的难点：复杂表格、数学公式、双栏/多栏布局、页眉页脚混入正文、扫描件 vs 电子件。

### 2.2 主流方案对比

**（1）轻量级：PyMuPDF4LLM（当前 baseline 方案）**

把 PDF 直接转为 Markdown，保留标题层级，提取表格为 Markdown table。

- 优势：纯 Python，无需 GPU，速度快（50 页约 5-10 秒），原生 PDF 文字提取尚可
- 局限：不含 OCR，扫描件无法处理；复杂嵌套表格易错位；公式识别弱；双栏阅读顺序可能出错

**（2）中量级：Marker**

pipeline 架构：Surya 布局检测 → Surya OCR（可选）→ 文本提取 → Markdown 输出。

- 优势：表格和公式处理优于纯规则方案；多语言支持好；自动过滤页眉页脚
- 局限：依赖 PyTorch 模型，需 4-8GB 显存；CPU 模式慢（50 页 5-15 分钟）；公式不支持 LaTeX 输出

**（3）重量级：MinerU**

完整版面分析管线：布局检测 → 阅读顺序恢复 → 元素识别 → 结构化输出。

- 优势：**公式自动转 LaTeX**（本赛题关键优势）；阅读顺序恢复强；中文优化好；OmniDocBench 表现领先
- 局限：需 CUDA GPU（推荐 8GB+）；安装复杂；内存占用大；CPU 下 30-60 秒/页

**（4）视觉语言模型级：olmOCR**

用精调的 7B VLM 直接把 PDF 页面转成结构化纯文本，不用传统 OCR + 版面分析流水线。

- 优势：绕过复杂版面分析；对扫描件、手写、低质量 PDF 处理强；开源可本地部署
- 局限：需 GPU；中文质量未知；输出纯文本而非 Markdown；表格公式不如 LaTeX 精确

### 2.3 本赛题的 PDF 解析选型建议

| 环境 | 推荐方案 | 理由 |
| --- | --- | --- |
| 纯 CPU | PyMuPDF4LLM + 预处理优化 | 无 GPU 时的唯一选择 |
| GPU（8GB+） | MinerU | 公式/表格/阅读顺序三项核心能力突出 |
| GPU（16GB+） | MinerU + olmOCR 互补 | MinerU 处理结构化文档，olmOCR 处理扫描件 |

### 2.4 预处理阶段可以做的工作

1. **页眉页脚过滤**：正则匹配重复出现的页码、章节标题、公司名称
2. **表格后处理**：格式校验（行列数一致、数值列对齐），异常时回退手动提取
3. **公式补标注**：在公式附近插入描述性文本帮助 LLM 理解
4. **段落合并**：按标点和语义合并被解析成多行的同一段落
5. **文档结构标注**：为每段标注所属章节路径，增强检索上下文

## 3. RAG 检索优化

要突破 17% 的准确率天花板，第一步就是引入检索模块，但必须注意检索引入的连贯性断裂风险。

### 3.1 分块策略

- **固定大小分块**：实现简单但容易切断语义
- **滑动窗口分块**：相邻块重叠 10%-20%，减少边界信息丢失
- **语义分块**：按段落、章节等自然边界切分，Markdown 天然适合
- **多粒度分块（Small-to-Big / Parent-Child）**：
  - 子块（200-500 token）用于向量检索，嵌入更聚焦，精度更高
  - 父块（800-2000 token）包含完整上下文，命中子块后取出父块送给 LLM
  - 实验表明该方案准确率比单一大块方案高 10%-15%

> **推荐起步方案**：按 Markdown `##` 标题切分 + 滑动窗口，块大小 800-1200 token，重叠 15%。有精力升级到多粒度分块（子块 400 token 检索 + 父块 1200 token 回答）。

### 3.2 混合检索

- **BM25** 对精确匹配敏感（数字、条款编号），但无法理解语义
- **向量检索** 能捕捉语义相似性，但对数字和年份不够敏感

混合检索 = BM25 + 向量检索，两路同时召回，结果融合。融合方式：

- **简单合并去重**
- **RRF（Reciprocal Rank Fusion）**：`score(d) = Σ 1/(k + rank_i(d))`，k 通常取 60
- **加权分数融合**：归一化后按权重加和（如 BM25 0.3 + 向量 0.7）

实现要点：BM25 用 rank-bm25 + jieba；两路各召回 20-30 个片段，融合后取 top 10-15。

> ⚠️ **注意**：经向赛题方确认，Embedding 模型和 Rerank 模型**不允许在正式提交中使用**。以下 BGE 系列内容仅供扩展学习。

**BGE 模型系列速览（扩展学习）**

| 模型 | 参数量 | 特点 |
| --- | --- | --- |
| bge-large-zh-v1.5 | 326M | 中文专用，C-MTEB 前列 |
| bge-m3 | 568M | 多语言，8192 token，dense + sparse |
| bge-reranker-base | 278M | 轻量，CPU 可跑 |
| bge-reranker-v2-m3 | 568M | 多语言，与 bge-m3 配套 |

**视觉检索：ColPali / ColQwen**

把 PDF 页面渲染成图像，用 VLM 直接从页面图像提取 patch 级嵌入做检索，完全绕过 OCR、版面分析、Markdown 转换。优势是绕过解析所有问题、布局信息天然保留；局限是需 VLM（3B+，GPU 必须）、返回粒度是整页、中文效果待验证。属于实验性方向。

### 3.3 重排序

- **Cross-Encoder 模型**：把"问题 + 候选片段"拼接后直接输出相关性分数
- **LLM-based Rerank**：用 LLM 自己打分，灵活但慢且耗 token

### 3.4 查询增强

缩小用户口语化提问与文档专业术语之间的语义差距。具体见 3.6 节的 HyDE。

### 3.5 片段组装

- **去重**：滑动窗口导致相邻片段重叠，需去重
- **排序**：按文档原始顺序排列（而非相关性分数），保持逻辑流
- **截断**：总 prompt 长度受 token 预算限制，在片段数量和质量间取舍

### 3.6 前沿 RAG 范式

传统 RAG 有三个根本缺陷：**扁平化、局部性、无反思**。下面的范式各自针对其中一个或多个缺陷。

**GraphRAG（Microsoft, 2024）**：从文档提取实体和关系构建知识图谱，再基于图谱检索推理。流程：实体关系抽取 → 知识图谱构建 → 社区检测（Leiden）→ 社区摘要生成 → Local Search（局部，事实查找）/ Global Search（全局，对比理解，Map-Reduce）。跨文档对比题和多文档联合推理题是 GraphRAG 的最优场景。代价是预处理需大量 LLM 调用，可离线完成。

**LightRAG（香港大学 HKUDS, 2024）**：GraphRAG 的轻量替代，不依赖社区检测，用**双向量索引**（实体向量 + 关系向量）+ 关键词引导查询同时支持局部和全局检索。支持**增量更新**——新文档加入只需提取新实体关系，不需重建索引。适合作为从标准 RAG 向图 RAG 过渡的第一个实验方案。

**StructRAG（2024）**：不同任务需要不同知识组织方式，定义五种结构类型：

| 结构类型 | 适用任务 | 组织方式 |
| --- | --- | --- |
| 表格 | 统计类 | 结构化行列 |
| 图 | 长链推理 | 实体-关系网络 |
| 算法 | 规划类 | 步骤流程 |
| 目录 | 总结类 | 层级分类 |
| 片段 | 简单单跳问答 | 原始文本块 |

启示：不同题型应该用不同的知识组织方式，按题型分派检索策略可能比统一框架更有效。

**RAPTOR（2024）**：用树结构解决"扁平检索丢失全局上下文"。构建：叶子层（基础块）→ GMM 软聚类 → LLM 摘要 → 递归 → 多层树。检索时按问题复杂度选层级：简单事实从叶子层，中等复杂度从中层摘要，全局理解从顶层。行业研报和跨年度对比题是 RAPTOR 优势场景。变体：adRAP（增量）、postQFRAP（后处理）。

**Self-RAG（2024）**：检索 + 反思 + 重试循环。按需检索 → 检索 → 对每个片段评估（相关性/支持度/有用性）→ 对低质量片段重新检索 → 生成时标注来源和可信度。

**CRAG（Corrective RAG, 2024）**：在 Self-RAG 基础上加自动纠错。用检索质量评估器打分（0-1），分三级：
- ≥0.7（CORRECT）：直接使用
- 0.3-0.7（AMBIGUOUS）：保留 + 换关键词补充检索
- ≤0.3（INCORRECT）：丢弃检索，切换全文阅读

本赛题适配：CORRECT → 直接用；AMBIGUOUS → 换关键词或扩大范围；INCORRECT → 回退到 baseline 硬截断 fallback。

**HyDE（2023）**：解决"用户问题用词和文档用词不一致"。先让 LLM 凭空生成假想"理想答案"，再把假想答案（而非原始问题）转向量检索。假想答案是文档风格（含专业术语），更易匹配真实片段。代价是每次多一次 LLM 调用，但召回率提升 10%-20%。

> 根据《Searching for Best Practices in RAG》（2024）评测，**HyDE + 混合检索（BM25 + 向量）是目前综合表现最好的默认配置**。

**KAG（2024）**：针对专业领域 RAG，引入领域知识对齐。本赛题启示：如果用 GraphRAG/LightRAG 做实体抽取，需定制实体类型（产品名称、条款编号、计算公式、数值、条件判断）和关系类型，而非用通用 prompt。

**多跳推理 RAG**：答案需通过多个片段的推理链推导。改进方案：Iterative RAG（迭代检索）、IRCoT（检索与思维链交替）、Beam Search RAG（束搜索多条推理链）。

**Agentic RAG**：把检索决策权交给 LLM，通过 Function Calling 自主决定是否检索、搜什么、搜几次、质量差怎么办。Baseline 测试过 FC，Token 消耗比 no-tool 高约 18%，但灵活性是提升准确率的关键路径。

### 3.7 本赛题的 RAG 路线建议

| 阶段 | 方案 | 预期收益 | 风险 |
| --- | --- | --- | --- |
| 1 | BM25 检索 + 语义分块 | 解决"答案不在前 4000 字" | 连贯性断裂，可能降分 |
| 2 | + 多粒度分块（子块检索 + 父块回答） | 缓解连贯性断裂 | 实现复杂度增加 |
| 3 | + 混合检索 + HyDE | 提升召回，改善口语化匹配 | 需 Embedding，多一次 LLM 调用 |
| 4 | + Rerank 精排 | 提升精确率 | 额外计算开销 |
| 5 | + 动态记忆压缩 | 有限预算保留最多有效信息 | 过度压缩丢关键条件 |
| 6 | + Bash 工具（Python 计算） | 消灭公式计算题算术错误 | 需设计沙箱 |
| 7 | + CRAG 自检机制 | 减少低质量检索错误 | 需设计评估器 |
| 8 | LightRAG（跨文档题） | 解决跨文档联合推理 | 预处理 Token 消耗 |
| 9 | Agentic RAG（FC 编排） | 灵活应对不同题型 | Token +18% |
| 10 | smolagents Code Agent | 减少 30% 推理步骤 | 需学习框架 |

> 建议每完成一个阶段就跑一次 历史评测提交，验证实际收益，避免"加了优化反而降分"的陷阱。

## 4. 上下文管理与动态记忆压缩

赛题名称里就有"动态记忆压缩"，这定义了本赛题的核心技术挑战。

### 4.1 问题的本质：上下文窗口是稀缺资源

每道题的推理链路：`读文档 → 提取信息 → 判断 → 输出答案`。每步消耗 Token，但预算有限（500 万）。核心问题：**给定 Token 预算 B，如何从候选信息池中选择子集，使模型回答正确的概率最大化？**

候选信息池：文档原文片段、上一步推理中间结果、题目和选项、Prompt 模板、验证/自检的二次推理结果。

### 4.2 动态截断

让模型自己决定什么时候停止阅读：分段读取，每读一段判断"信息是否足够"。按题型设定不同阅读预算：事实查找题读前 2000 字符；跨文档对比题每份 1000 字符；公式计算题读到公式就停。

### 4.3 信息密度控制

保险条款和监管法规有大量模板化文本（"本合同的构成""投保须知"），可预处理时过滤，或检索时对"释义""名词定义"章节降权。按题型定义信息价值函数：计算题公式段落权重最高，条款定位题例外条件段落权重最高。

### 4.4 动态记忆压缩：分层存储与选择性遗忘

**工业界实践：Agent 的记忆分层**

**Kimi Code CLI 的 Context Compaction**：超过 token 阈值自动触发，按优先级保留：① 当前任务状态 ② 错误与解决方案 ③ 代码最终版本 ④ 系统上下文 ⑤ 设计决策 ⑥ TODO。本赛题对应优先级：

1. 题目完整文本和所有选项（最高，绝不压缩）
2. 从文档提取的公式、数值、条件判断（核心证据）
3. 检索原文片段中与题目直接相关的部分
4. 文档章节标题和结构信息
5. 中间推理过程摘要
6. 经判断不相关的原文（最低，优先丢弃）

**Hermes 的 Trajectory Compressor**：完整压缩管线。第一步计算压缩需求（tokenizer 计数）；第二步确定受保护区域（头部：首个 system/human/gpt/tool；尾部：最后 N 个 turns）；第三步计算压缩区域；第四步 LLM 生成摘要（`[CONTEXT SUMMARY]:` 前缀，目标 750 tokens）；第五步组装。迁移到本赛题：

- **"首"**：题目文本 + 选项（不可压缩）
- **"尾"**：最终推理步骤（列公式 → 代入 → 计算 → 对比 → 输出，必须完整保留）
- **"中间"**：文档阅读过程，可压缩为结构化摘要（数值精确、标注出处）

**Claude Code 的四层渐进压缩**：从便宜到贵逐级尝试，只有低层搞不定才升级：

```
Layer 1: Snip（裁剪工具输出）→ 免费，不调 LLM
Layer 2: Microcompact（基于 prompt cache 的轻量压缩）
Layer 3: Context Collapse（折叠搜索/读取为摘要）
Layer 4: Autocompact（LLM 全量总结）→ 最贵
```

启发：检索片段太长先 Snip（保留关键词段落 + 前后各一段），仍超预算再调 LLM 摘要。不要一上来就让模型总结。

**Codex 的 Memento 策略：为什么不能只留摘要**

压缩后的历史不是纯摘要，而是 `initial_context + 精选 user 消息 + summary + 最近 N 条`。因为 LLM 生成的 summary 会丢失精确信息。比如"因意外伤害发生上述情形的，无等待期"可能被总结为"等待期内一般不赔"，关键例外信息就丢了。本赛题压缩时至少保留三类信息不被摘要化：

1. 题目原文（包括选项）
2. 从文档提取的精确数值和公式
3. 包含例外条件的条款原文

**generic-agent 的 L1-L4 记忆层级**

- **L1 全局内存索引**（≤30 行，<1k tokens）：场景关键词 → 记忆定位映射 + RULES（避坑准则）
- **L2 全局事实库**：环境特异性事实（IP、路径、凭证、配置常量）
- **L3 任务级精简记录库**：特定任务的极简 SOP 和工具脚本
- **L4 历史会话层**：原始对话记录，按需检索

核心公理：① **行动验证原则**（No Execution, No Memory）② 神圣不可删改性 ③ 禁止存储易变状态 ④ 最小充分指针。

映射到单题推理：L1 = 题目结构化索引；L2 = 从文档提取的硬事实（公式、数值表、条款编号）；L3 = 题型推理 SOP；L4 = 完整文档原文。

**学术界：MemGPT（UC Berkeley, 2023）**

类比操作系统虚拟内存：主上下文（物理 RAM）+ 外部上下文（磁盘）。关键创新是 **LLM 自己控制"换页"**，通过 Function Calling 主动管理记忆。映射到本赛题：

| MemGPT 概念 | 本赛题等价物 |
| --- | --- |
| 主上下文 | 当前题目的 prompt，受单题 Token 预算约束 |
| 外部上下文 | 文档全文（已解析 Markdown），不受单题预算约束 |
| 换页决策 | 判断检索结果是否足够，不够则检索更多 |
| 档案记忆 | 文档的 BM25/向量索引 |

关键差异：本赛题是"长文档 + 短推理"，MemGPT 是"短文档 + 长对话"。所以"换页"应调整为"分段读取 + 渐进压缩"。

### 4.5 实现建议：从策略到代码

**触发策略**

```
需要压缩 = (当前 prompt tokens >= 模型上下文窗口 × 0.7)
         或 (当前 tokens + 预计下一轮检索 tokens >= 模型上下文窗口)
```

0.7 阈值给后续推理留 30% 余量。Qwen-plus 从 2025-07-28 快照版本起支持 1M 上下文（默认 128K）。

**保留策略（Memento 模式）** 按优先级从高到低：① System prompt + 题目原文（不压缩）② 精确数值和公式（保留原文）③ 例外条件条款原文 ④ 中间推理步骤（可压缩）⑤ 已读未用段落（丢弃）。

**结构化摘要模板**

```
[CONTEXT SUMMARY]
Goal: 判断四款产品的身故保险金高低
Documents Read: doc_1（平安智盈金生）、doc_2（国寿增益宝）
Key Formulas Extracted:
  - 平安智盈金生: 身故保险金 = max(已交保费, 现金价值)
  - 国寿增益宝: 身故保险金 = 基本保额 × 年龄系数
Numerical Values:
  - 平安: 已交保费=100万, 现金价值=90万 → max = 100万
  - 国寿: 基本保额=90万, 系数=1.6 → 144万
Pending Verification: 文档 3 和文档 4 尚未读取
```

结构化的 Key Formulas 和 Numerical Values 不会被 LLM 总结语言"改写"导致精度丢失。

## 5. 答案验证与多轮推理

### 5.1 自检机制

1. 第一轮：让模型根据上下文生成答案
2. 第二轮：让模型验证自己的答案，检查每个选项的证据是否充分
3. 如果不一致，回退到第一轮重新生成

### 5.2 常见错误模式

- **否定词遗漏**：文档说"不适用"，模型读成"适用"
- **年份混淆**：题目问 2025 年数据，模型用了 2024 年
- **条件遗漏**：只读到"免赔额 5000 元"，漏掉"意外伤害 0 免赔"
- **跨文档混淆**：把文档 A 的公式套到文档 B 的场景

可在 prompt 中针对这些错误模式加入显式检查指令。

## 7. Agent 化方向

### 7.1 Function Calling 方案

Baseline 测试过 FC，Token 消耗比 no-tool 高约 18%。优势在于模型可自主决策"什么时候搜、搜什么"。适合 FC 的场景：跨文档题、信息不足需补搜的场景。

### 7.2 多步推理

从"读文档 → 答问题"升级为"读文档 → 提取关键信息 → 判断信息是否足够 → 不够则继续搜索 → 综合推理 → 输出答案"。

### 7.3 终端 Agent 与 Bash 工具

**LLM 的计算短板**：大语言模型本质是"文字接龙"引擎，不是计算器。多步数值计算错误率显著高于使用 Python 解释器辅助的方案。

**解决方案：让 LLM 写代码而不是算答案。** 不让 LLM 自己算，而是让它写 Python 代码，用 Bash 工具执行，再把结果还给 LLM 做最终判断。这是终端 Agent（Terminal/Coding Agent）模式。

```python
# 国寿增益宝
basic_amount = 900000   # 基本保额 90 万
coefficient = 1.6       # 40 岁对应系数
guoshou = basic_amount * coefficient

# 平安智盈金生
total_premium = 1000000  # 已交保费 100 万
account_value = 900000   # 保单账户价值 90 万
pingan_zhiying = max(total_premium, account_value)

results = sorted([
    ("国寿增益宝", guoshou),
    ("平安智盈金生", pingan_zhiying),
], key=lambda x: x[1], reverse=True)
print(results)
```

**为什么 Bash 工具比 Function Calling 更适合计算**：FC 的 `calculator()` 不能写多步逻辑、不能做数据整理。Bash 工具给模型一个完整的编程环境，模型可以自己决定先算哪个、中间结果怎么存、最终怎么排序。

**参考架构：ReAct 循环 + Bash 工具**

```
Thought（思考）→ Action（行动）→ Observation（观察）→ Thought → ...
```

实现建议：

- tools 定义中加入 `execute_python(code: str)` 工具
- 工具描述明确：用于精确数值计算，不要用 LLM 自己做算术
- 在沙箱中执行（subprocess 或 exec），返回 stdout/stderr
- 代码执行超时设为 5 秒，防死循环
- 代码报错时把错误返回给模型自己修

> 额外收益：Bash 执行的 Token 消耗远低于让模型一步步推理。一段 Python 50 token + 结果 10 token；同样计算用 CoT 可能需 200+ token。

### 7.4 smolagents：用 Code Agent 范式重新组织工具调用

smolagents（HuggingFace, 2025，GitHub 24,000+ 星）的核心理念：**让 Agent 通过编写 Python 代码执行操作，而不是 JSON 格式的工具调用**。

**传统 Tool Calling vs Code Agent**

传统 FC：每步 JSON 序列化/反序列化，一次只能调一个工具，无法写条件判断、循环、中间变量。

Code Agent：模型直接写一段 Python 代码，一次性执行完毕，中间结果自动传递。

**效率提升**：据 HuggingFace 实验，Code Agent 比 JSON Tool Calling **减少约 30% 推理步骤**。原因：批量操作、变量传递、条件逻辑、模型原生代码能力强。

**与 baseline 的对比**

| 维度 | baseline (no-tool) | smolagents 进阶版 |
| --- | --- | --- |
| 文档处理 | 硬截断前 4000 字符 | BM25 检索 + Code Agent 自主决定搜索策略 |
| 计算能力 | LLM 直接推理（易出错） | Python 代码执行（精确） |
| 推理模式 | 单轮 | ReAct 多轮循环 |
| 跨文档 | 所有文档拼接截断 | Code Agent 逐份搜索、聚合计算 |
| Token 效率 | 固定消耗 | 按需搜索，代码执行不消耗 LLM Token |
| 实现复杂度 | 低 | 中（需理解 smolagents 框架） |

进阶 baseline 集成方案目录结构示例：

```
advance-baseline/
├── src/
│   ├── agent/
│   │   ├── smol_agent.py       # smolagents CodeAgent 主逻辑
│   │   └── tools.py            # 自定义工具：文档搜索、BM25检索、Python执行
│   ├── data/loader.py          # 题目加载 + 文档读取（复用 baseline）
│   ├── evaluation/evaluator.py # 答案校验与格式化
│   └── utils/llm_client.py     # LLM 客户端（复用 baseline）
├── config.yaml
├── requirements.txt
└── run_agent.py                # 入口
```

关键设计决策：自定义工具集（`search_document`、`execute_python`）、模型无关（LiteLLM 适配）、安全执行（限制危险模块 import）、Token 预算控制。

## 附录 A：技术概念速查

### A.1 什么是 Agent（智能体）

Agent 指大语言模型不再只做"你问我答"，而是能主动观察环境、做决策、调用工具、并根据反馈调整下一步行动。

- **单次调用**：一问一答，无后续动作
- **工作流（Workflow）**：每步提前写死，模型按顺序执行
- **Agent**：给目标，模型自己决定步骤，遇到问题会回退重来

本 baseline 的硬截断不算真正的 Agent，因为它没有任何决策能力。

### A.2 Embedding 与向量检索

Embedding 把文本转成数字向量，**意思相近的文本在向量空间中位置也相近**。向量检索把片段向量存数据库，问题转向量后计算相似度（常用余弦相似度，0-1 区间，0.8 以上算相似）取 top K。

| 维度 | 关键词搜索（BM25） | Embedding 向量检索 |
| --- | --- | --- |
| 匹配依据 | 词是否相同 | 语义是否相近 |
| "退保费用"搜"退保手续费" | 搜不到 | 能搜到 |
| 对数字/年份敏感度 | 高 | 低 |
| 计算开销 | 低 | 高（需 GPU/专用模型） |

### A.3 Rerank（重排序）

初步检索追求速度，结果可能混入"看似相关但不精确"的片段。Rerank 用 Cross-Encoder 对 top K 逐一打分精排。流程：粗排（召回 50-100）→ 精排（Rerank）→ 取 top 5-10。

### A.4 BM25

基于词频统计的检索算法。`得分 = Σ TF × IDF`：词频（TF，对数饱和处理）× 逆文档频率（IDF）。优点：纯统计、速度快、对精确匹配敏感、实现简单。缺点：无法理解语义、对同义词无能为力、长文档天然占优。

### A.5 Token 与上下文窗口

Token 是模型处理文本的基本单位。中英文换算：1 个英文单词 ≈ 1-2 Token，1 个汉字 ≈ 1-1.5 Token，数字逐位拆分。

**上下文窗口**是模型一次能处理的 Token 上限。Qwen-plus 支持 1M（默认 128K）。实际使用有两个约束：

1. **经济约束**：500 万总预算 / 100 题 = 平均每题 5 万 Token。塞 10 万字年报全文，一题就花掉 10 万 Token，超预算
2. **注意力衰减**：模型对 prompt 中间部分记忆下降（"中间丢失"问题）

这就是"动态记忆压缩"的核心挑战：在"保留足够信息"和"控制 Token 消耗"之间取舍。

## 附录 B：五类金融文档背景速查

### B.1 保险条款

典型结构：保险责任（保什么）、责任免除（不保什么，条款定位题高频考点）、保险期间与等待期（意外伤害常例外）、保险金额与保费、退保与现金价值（计算公式差异大）、释义。

答题关键：计算题精准定位公式和年限系数；等待期题找"意外伤害"例外；免责题到"责任免除"逐条核对；跨产品比较同时打开多份。

### B.2 监管法规

典型结构：总则/适用范围、具体义务、时限要求、例外条款（"但书"是考点）、罚则。

答题关键：法条引用找原文出处；时限题精确定位天数/工作日；适用范围注意"除外"条款；注意法规间冲突或补充关系。

### B.3 财务报表

三大报表：

- **资产负债表**：资产 = 负债 + 所有者权益
- **利润表**：营业收入 - 营业成本 - 费用 = 净利润
- **现金流量表**：经营/投资/筹资三类，经营活动现金流量净额是核心

| 指标 | 公式 | 含义 |
| --- | --- | --- |
| 毛利率 | (营业收入 - 营业成本) / 营业收入 | 产品盈利能力 |
| 净利率 | 净利润 / 营业收入 | 最终盈利能力 |
| ROE | 净利润 / 平均股东权益 | 股东资本回报 |
| 研发投入占比 | 研发费用 / 营业收入 | 对研发的重视程度 |

答题关键：跨年度/跨公司对比注意指标口径一致；增长率确认基期；注意"归属于母公司股东的净利润"和"净利润"的区别。

### B.4 金融合同

主要是债券募集说明书和债券条款。典型结构：发行概况、募集资金用途、评级信息、增信措施、特殊条款（回售/赎回/调整票面利率/交叉违约）。

答题关键：条款判断定位原文；计算题确认时间节点和利率；区分"主体评级"和"债项评级"。

### B.5 行业研报

典型结构：行业概况、竞争格局、驱动因素、数据与预测、投资建议。

答题关键：事实查找注意年份限定；数据有来源标注但模型可能混淆；研报观点（"我们认为"）和数据事实要区分，观点不一定正确。
