# FinDocQA 本地评测标准

## 1. 目标

在没有比赛排行榜反馈时，用一套固定、可复现、可人工审计的本地评测体系判断改动是否真正提升系统，而不是依赖“感觉答案更好”。

评测原则：

> 固定题集 + 固定金标 + 分阶段指标 + 错误簇复核 + 版本对比。

比赛原项目和历史题目不删除，继续保留在私有历史仓库中；FinDocQA Public 仓库只保留评测框架、脱敏示例和不受比赛数据授权限制的公开样例。

## 2. Gold Set 怎么来

### 2.1 第一阶段：从现有高置信题目建立种子集

优先选取已经经过多次人工核对、证据明确、答案争议小的题目，而不是随机抽题。

建议初始规模 50～100 题，覆盖五个领域：

- 金融合同
- 财务报告
- 保险条款
- 监管文件
- 研究报告

同时覆盖主要题型：

- 单文档事实题
- 多选/逐选项判断
- 数值计算
- 表格取数
- 跨文档比较
- 排序/筛选
- 否定、条件、例外
- 时间/版本约束
- 多跳证据

### 2.2 历史提交如何作为候选证据

历史排行榜只用于**筛选 Gold 候选**，不能直接替代原始文档真值。

建议按可归因强度分级：

```text
S 级：单题提交，且除了答案字段外其他字段完全不变；分数方向明确
A 级：小批量提交，且仅答案字段变化；总增益与改动题数高度一致
B 级：小批量提交有净增益，但无法确认每一道题分别贡献多少
C 级：仅来自最终高分版本、模型共识或人工直觉，没有独立反事实验证
N 级：单题错误改动导致明确降分，可作为负向对照候选
```

使用规则：

- `S/N` 级优先进入第一轮人工核验；
- `A` 级逐题回到原文确认后才可升级；
- `B/C` 级只进入候选池，不因为“最终版本分数高”就直接当 Gold；
- 所有等级最终都必须满足“原始文档证据闭环”才能成为正式 Gold。

特别注意：如果一次提交同时改变了答案、Token、reasoning、模型输出或其他评分相关字段，就不能把分数变化简单归因于答案修改。

### 2.3 第一版候选池与实际冻结规模

当前 30 题只是候选池，不是必须冻结的数量。正式 Gold 数量由证据完整度决定：

```text
候选 30 题
→ 自动生成文档 / 页码 / 逐选项证据
→ Evaluator 独立复核
→ 能闭环多少就冻结多少
→ 其余保留为 Candidate / Disputed / Future
```

第一版可以只有 `8～20` 道本地 Gold；不足 8 道时也不得降低标准，而应明确本地轨道尚未具备主评分资格。覆盖目标是五个金融领域和主要题型，但覆盖目标不能覆盖 Gold 真实性门槛。

本地 Gold 不单独承担全部评测职责。正式评测套件由以下轨道组成：

```text
本地真实文档 Gold
+ FinQA / TAT-QA 等外部公开评测
+ 历史 Failure-Regression
+ Holdout-Shadow
```

外部数据负责检验公开标准能力和泛化；本地 Gold 负责检验当前 190 份文档上的真实端到端能力。两类指标分轨展示，不混成一个无法解释的总分。

### 2.4 尽量减少人工确认

Gold Set 不要求仓库所有者把每道题从头人工重做一遍。更合理的是“机器先收集证据，人工只做最终裁决”。

建议把标注流程拆成：

```text
历史提交 / 现有高置信答案
→ 自动定位候选文档
→ 自动抽取页码与证据片段
→ 自动生成 Claim / 计算过程
→ 机械一致性检查
→ 人工只确认：答案是否由这些证据充分推出
```

对于 `S/A` 级历史强锚点，人工主要检查原文证据与题意是否一致，不需要重新探索答案空间。

对于确定性计算、原文直接事实、明确法规条文等案例，如果文档、公式、单位和输入值都能机械复算，可以采用“自动复算 + 一次人工抽查”作为第一版 Gold 的准入方式；只有存在语义歧义、跨文档缺证或选项边界争议时才进入双人/双轮仲裁。

因此第一版应优先挑“容易证明正确”的题，而不是“最难的题”。难题可以放到 Gold-Hard，等标注体系稳定后再补。

### 2.5 如何避免对 Gold Set 过拟合

Gold Set 本身可以全部是高确定性题，但**不能让全部 Gold 都参与日常调参**。

推荐冻结三层：

```text
Dev-Core
  日常可看单题结果，用于开发和回归

Holdout-Shadow
  有金标，但日常只看汇总分，不根据单题结果改规则

Fresh-Challenge
  后续持续补充的新题，阶段性验证泛化
```

本地 Gold 数量确定后再划分：

```text
约 70% Dev-Core
约 20% Holdout-Shadow
约 10% Fresh/Rotation 预留
```

题量较小时优先保证至少一个 Shadow；不足以合理分层时，先只冻结 Dev-Core，并明确 Shadow 尚未建立。

当候选池扩到 50～100 题后，再扩大 Holdout 比例。

关键纪律：

- 同一题被用于设计规则、Prompt、qid 特例或人工错误分析后，它就属于 Dev，不再算真正的 Holdout；
- Shadow 运行时优先只暴露聚合指标，阶段结束后才展开单题错误；
- 每修复一类错误，可以把旧题加入 Failure-Regression，但同时应补一批同类型、未参与开发的新题；
- A/B 榜历史题可以提供高确定性真值，但不能让整个 Benchmark 都来自过去的排行榜调优轨迹；
- 后续应持续加入公开数据集或新人工构造题，验证能力是否迁移到未见文档和未见问法。

### 2.6 每道题必须保存的金标

每题至少包含：

```text
case_id
question
domain
question_type
gold_answer
required_documents
gold_evidence_pages
gold_evidence_snippets
critical_claims
calculation_or_reasoning_notes
annotation_status
annotation_source
```

其中最重要的不是只有 `gold_answer`，而是同时保留：

```text
答案是什么
+ 为什么
+ 来自哪份文档
+ 哪一页/哪一段
+ 哪些 Claim 必须成立
```

这样才能判断错误到底发生在文档召回、证据定位、推理、计算还是最终输出。

## 3. 怎么判断 Gold Set 本身合理

一道题只有满足下面条件，才进入正式 Gold Set：

1. **答案可由原始文档独立推出**，不能依赖排行榜分数或模型多数票。
2. **证据可定位**到明确文档、页码和局部文本/表格。
3. **题意边界明确**，不存在多个同样合理的解释；有争议的题进入 `disputed` 集，不计主分。
4. **至少两次独立复核**。重要或复杂题建议两个人/两轮独立标注后再仲裁。
5. **模型不可见金标**。运行时不能把答案、required_documents 或 gold evidence 泄露给待测链路。
6. **题目具有代表性**，不能全部是容易题，也不能全部来自某一个错误簇。

正式状态建议：

```text
DRAFT
→ REVIEWED
→ GOLD
→ DISPUTED / RETIRED
```

只有 `GOLD` 题进入主评分。

## 4. 不再只看一个“总正确率”

FinDocQA 应分层评分。

### 4.1 文档范围

衡量是否先找对文档：

- Required Document Recall@1 / @3 / @5
- 多文档题 Complete Recall@K
- 错召回文档数量

### 4.2 证据定位

衡量找对文档后是否定位到正确位置：

- Evidence Page Recall@K
- Evidence Hit Rate
- 必要 Claim 的证据覆盖率
- 无证据/错页/错表比例

### 4.3 最终答案

按题型分别计算：

- 单选/多选：Exact Match、集合 Precision / Recall / F1
- 数值：精确匹配或规定容差内正确率
- 文本：规范化 Exact Match + 人工语义复核
- 排序/列表：顺序正确率、集合完整率

### 4.4 Claim 与验证

衡量“答案对，但理由是否真的站得住”：

- Claim SUPPORT / REFUTE / UNRESOLVED 准确率
- Claim Evidence Binding 准确率
- 错误证据放行率（False Accept Rate，应尽量低）
- 正确答案被错误 Gate 阻断率（False Reject Rate，应尽量低）
- Correct-but-Blocked 数量：答案正确但生产门禁拒绝
- Incorrect-but-Accepted 数量：答案错误但生产门禁放行

最终答案正确率和生产门禁可靠性必须分开统计：门禁阻断不等于模型没有产出答案，模型答对也不等于可以安全放行。

### 4.5 工程指标

同时记录：

- Prompt Token
- Completion Token
- 总 Token
- 模型调用次数
- Recovery 次数
- Provider/格式失败数
- 单题耗时

质量上升但 Token 或恢复次数暴涨，也不能直接视为有效优化。

## 5. 推荐的主评分方式

第一阶段不要设计过度复杂的综合分，先保留四个核心面板：

```text
A. Answer Accuracy
B. Document/Evidence Recall
C. Verification Reliability
D. Cost / Stability
```

任何代码改动至少满足：

```text
主目标指标提升
且
核心回归题不显著下降
且
错误证据放行率不恶化
且
成本增长在可接受范围
```

正式晋级建议采用“硬门槛 + 指标提升”，而不是简单加权总分。

例如：

```text
答案准确率不得下降
关键 Gold Case 不得新增错误
Evidence Recall 不得明显下降
错误证据放行率不得上升
满足以上条件后，再比较目标能力指标是否改善
```

## 6. 数据集分层

不要让所有题都承担同一个职责。

建议分成：

```text
Gold-Core
  40～60题
  每次修改必跑，稳定回归

Gold-Hard
  20～40题
  复杂计算、多文档、条件/例外等高难题

Failure-Regression
  持续增加
  每修复一个真实 bug，就加入对应回归案例

Shadow
  不参与日常调参
  用于防止对 Gold-Core 过拟合
```

最重要的是 `Shadow`：开发时不能反复根据它调规则，只在阶段性版本时运行。

## 7. 比赛历史题怎么处理

原 AFAC 项目先不删除。

它的作用改成：

```text
历史错误库
+ 已知高置信案例来源
+ 将来官方/高分答案公布后的校准来源
```

但不要把比赛排行榜答案直接当 Gold Truth。

如果未来官方公布标准答案或可靠高分解答：

```text
官方/公开答案
→ 回到原文逐题核验
→ 补齐证据页和 Claim
→ REVIEWED
→ GOLD
```

也就是说，排行榜可以提供“线索”，原始文档证据才是最终金标来源。

## 8. 建议的第一版实施顺序

```text
Step 1  以现有 30 题作为候选池，不预设最终数量
Step 2  自动生成答案候选、文档、页码、关键证据和 Claim 复核包
Step 3  Evaluator 先冻结少量高确定性本地 Gold
Step 4  注册 FinQA / TAT-QA 等现有外部评测轨道
Step 5  形成分轨 Evaluation Suite，而不是单一混合总分
Step 6  输出 Answer / Retrieval / Evidence / Verification / Cost 五类指标
Step 7  再扩充本地 Gold，并建立 Holdout-Shadow
```

第一版本地 Gold 宁可少，也不能为满足数量而降低证据与复核标准。
