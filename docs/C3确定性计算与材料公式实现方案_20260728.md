# C3 Deterministic Calculation：确定性计算与材料公式实现方案

日期：2026-07-28

## 1. 目标

C3 的目标不是“让大模型更会算”，而是把计算题拆成可审计、可复算的确定性链路：

```text
问题
→ 识别计算意图
→ 找公式 / 找变量
→ 检查公式是否完整
→ 绑定主体、指标、时间、单位与来源
→ 编译成受限 FormulaProgram
→ Decimal / Python 确定性执行
→ 结果复核
→ Solver 负责把结果说人话
```

核心原则：

> 公式或变量不完整时，宁可 REVIEW / FAIL，也不拿半条公式算出一个“精确的错误答案”。

---

## 2. 三层公式能力

### L1：系统内置通用公式

第一版优先支持 5 类：

```text
同比 / 增长率
差额
占比
百分点变化
排序比较
```

典型公式：

```text
growth_rate = (current - previous) / previous
difference = left - right
ratio = part / whole
percentage_point_change = current_rate - previous_rate
ranking = sort(values)
```

这类公式由系统维护，不依赖材料中是否显式给出公式。

### L2：材料显式公式

材料可能直接给出：

```text
赔付金额 = min((医疗费用 - 免赔额) × 给付比例, 责任限额)
```

L2 的难点不是算，而是判断公式是否被 PDF / 表格 / OCR 完整提取。

需要保留：

```text
FormulaEvidence
├─ raw_formula
├─ normalized_expression
├─ variables / variable definitions
├─ conditions / limits
├─ source refs
├─ local context
├─ linked tables
└─ completeness gate result
```

### L3：自然语言业务规则公式

例如：

```text
“超过免赔额的部分按 80% 给付，最高不超过 10 万元。”
```

需要先编译为：

```text
min(max(expense - deductible, 0) * 0.8, 100000)
```

L3 暂不在本轮自动执行范围内。第一版只把 L2 Gate 做严，避免把未编译的自然语言约束直接忽略。

## 4. 为什么不让 LLM 直接写 Python

不采用：

```text
LLM
→ 任意 Python 字符串
→ subprocess / eval
```

采用：

```text
材料公式 / 内置公式
→ FormulaProgram
→ 白名单 operator
→ Decimal executor
```

第一版白名单：

```text
identity
add
subtract
multiply
divide
min
max
abs
power（当前只允许整数指数）
sort_desc / sort_asc
```

因此：

1. 不执行任意 Python；
2. 不允许属性访问、任意函数、import、文件/网络操作；
3. 每一步都产生 trace；
4. 同样输入得到同样结果。

这部分借鉴 FinQA 的“program + execution”思想，但合同与实现保持 FinDocQA 自己的数据中立设计。

## 5. L2：Formula Evidence Gate 是核心

### 5.1 典型危险情况

真实材料：

```text
赔付金额 = expense × ratio
每次赔付最高不超过责任限额
```

如果只提取第一行：

```text
expense × ratio
```

Python 会算得非常准确，但业务结果可能错误。

因此第一版 Gate 检查：

```text
公式为空                         → FAIL
括号不闭合 / 明显截断            → FAIL
变量未绑定                       → REVIEW
没有来源 lineage                 → REVIEW
存在最高/不超过但公式没有 min    → REVIEW
存在至少/不低于但公式没有 max    → REVIEW
引用下表但没有 table ref         → REVIEW
出现续表/下页提示但缺上下页       → REVIEW
```

只有：

```text
PASS
→ Formula Compiler
→ Executor
```

REVIEW / FAIL 不执行。

### 5.2 为什么 REVIEW 和 FAIL 分开

```text
FAIL
= 当前公式本身已经明显坏了，例如截断、语法不完整。

REVIEW
= 公式可能是对的，但证据不够，例如变量在别页、比例来自下表、限制条件未编译。
```

后续 Recovery 可以针对 REVIEW 做：

```text
扩大同页前后块
→ 找关联表格
→ 找前后页
→ 查变量定义
→ 重新 Gate
```

## 6. 变量绑定要求

最终变量不能只是：

```text
A = 100
B = 80
```

目标合同：

```text
BoundVariable
├─ name
├─ value
├─ unit
├─ metric
├─ entity
├─ period
├─ definition
├─ source_ref
└─ confidence
```

例如：

```text
current_profit
→ 归母净利润
→ 招商银行
→ 2024
→ 100亿元
→ annual_report / P35 / table-row
```

第一版本地 Binder 只做保守的：

```text
name = 2万元
ratio = 80%
```

并自动做：

```text
亿元 → 元
万元 → 元
% → ratio
```

复杂的“表格行列 + 主体 + 时间 + 指标”绑定放到 C3 下一阶段。

```text

├─ registry.py
├─ compiler.py

├─ engine.py

```

长期收敛方向：

```text

```

## 8. 当前第一版已实现

### C3-A：通用内核

已实现：

- 5 类内置公式 Registry；其中排序方向拆成 `ranking_asc / ranking_desc`，无方向时 fail closed；
- `FormulaEvidence`；
- `BoundVariable` + lineage；
- `FormulaEvidenceGate`；
- `SafeFormulaCompiler`；
- `FormulaProgram`；
- Decimal executor；
- 计算 trace；
- 金额 / 百分比基础单位归一化；
- 材料显式局部公式提取；
- 材料局部显式变量绑定；
- 同名局部变量冲突检测：不同归一化值进入 `REVIEW`，等值可去重；
- 业务 `min/max` 限制采用保守 governing-root 证明：最终表达式根必须是对应 `min/max`，且限制 target 必须是根调用的直接变量参数；嵌套、算术包装或非 governing 分支统一进入 `REVIEW`；
- Formula / BoundVariable lineage 内容有效性 Gate；
- 不完整或不可审计公式 fail-closed。

### C3-B V1-R1：Formula Context Recovery（Executor 已修复两条 False Pass，待 Evaluator 复评）

已实现：

- 新增 `FormulaContextRecovery` / `FormulaRecoveryResult` / `FormulaRecoveryStep` 公共接口；
- Recovery 只依赖 `CanonicalDocument / CanonicalPage / CanonicalBlock / CanonicalTable` 和 `DocumentStore`，不直接读取 MinerU 私有结构；
- 同页按 `reading_order` 前后有限窗口恢复普通上下文块，默认前后各 2 个，reading order 缺失、重复或不连续时进入 `REVIEW`；
- 邻近 table / formula 不因“物理上靠近”自动拼入；表格只接受 `linked_table_refs / table_id / canonical metadata` 等显式 linkage；
- linked table 可补充 caption、markdown/headers/rows、table footnote，并保留自身 lineage；
- 跨页授权只接受公式 anchor 自身文本中的“见下页 / 见上页”等方向信号，或 anchor / 唯一 `CanonicalFormula.metadata` 中显式 continuation target；普通 same-page 邻块里的跨页词不能授权公式跨页；
- 跨页只允许 same doc 的相邻 `±1` 页；continuation 不唯一、方向/metadata 冲突或跨文档时 REVIEW / FAIL；
- 参与 Recovery 的 block/table source refs 全部合并、按来源身份去重；参与源缺自身 lineage 时保持 `REVIEW`；
- Formula-level footnote dependency 会同时检查 `FormulaEvidence.metadata`、anchor block metadata 和唯一 `CanonicalFormula.metadata`；当前 canonical contract 尚无可靠公式脚注 linkage 时返回 `unsupported_explicit_footnote_linkage`，不得 ready；
- Recovery 完成后重新执行 `LocalContextVariableBinder + FormulaEvidenceGate`，只有 Gate PASS 才 `ready_for_execution=True`；本阶段不接 CalculationSolver 主链。

### 当前明确未做

- PDF 跨页公式自动拼接；
- 表格 lookup 自动执行；
- 脚注与公式自动绑定；
- 同名变量的主体 / 时间 / 指标消歧；
- L3 自然语言规则自动编译；
- 多公式候选与问题语义的自动选择；
- 全面替换旧 `CalculationSolver` 的 subprocess 路径。

这些不应被评估者误判成“已经完成”。

## 10. 当前主线与后续阶段

继续按下面顺序推进，而不是直接增加几十种公式：

### C3-B：Formula Context Recovery（V1-R1 READY_FOR_REVIEW）

```text
公式块
→ 同页前后块
→ 关联表格
→ 脚注
→ 前后页
→ CanonicalFormula / CanonicalTable lineage
→ 重新 Gate
```

目标：先解决“材料公式提残了”。

### C3-C：Semantic Variable Binder

```text
变量
→ 指标
→ 主体
→ 时间
→ 单位
→ 文档 / 页 / 表格行列
```

目标：解决“公式对，但抓错数字”。

### C3-D：接入 CalculationSolver

只有在：

```text
Formula Gate PASS
+ Variable Binding PASS
+ 问题语义与公式匹配 PASS
```

时才让通用 C3 直接返回确定性结果。

否则走 Retrieval Recovery / Solver，而不是强算。

### C3-E：局部评测

建立独立 C3 benchmark：

```text
公式识别准确率
公式完整性 Gate False Pass / False Reject
变量绑定准确率
单位归一化准确率
计算结果准确率
lineage 完整率
```

其中最重要的是：

> Formula Evidence Gate 的 False Pass 必须极低，不能把残缺公式放进执行器。

## 12. 复评重点

评估者下一轮不要只看“18 个测试是否 PASS”，重点审查：

1. Gate 是否可能把残缺公式误判 PASS；
2. 变量 Binder 是否可能抓错同名数字；
3. `SafeFormulaCompiler` 是否真的无法执行任意代码；
4. 百分比与百分点语义是否分开；
5. 分母 0 / 缺变量 / 缺 lineage 是否 fail closed；
6. 是否错误宣称跨页、表格、脚注已经解决；
7. 是否与现有 `CalculationSolver` / 保险专项重复造轮子；
8. 下一步应优先补 Context Recovery，还是先接主链。
