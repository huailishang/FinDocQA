## 1. 最终目标结构

```text
                FinDocQA
                   │
        ┌──────────┴──────────┐
        │                     │
   文档生产链             问答消费链
        │                     │
各种输入                  Question
PDF/MD/TXT/HTML/JSON          ↓
已解析文档/外部数据集      题目理解
        ↓                     ↓
Source Adapter             文档范围
        ↓                     ↓
Parser / Importer          文档召回
        ↓                     ↓
Normalizer                证据检索
        ↓                     ↓
Quality / Repair          Rerank/去重/压缩
        ↓                     ↓
CanonicalDocument          Solver
        │                     ↓
        └──────────────→ Claim验证
                              ↓
                           Recovery
                              ↓
                         ResultRecord
                              ↓
                         Output Adapter
```

最核心的边界只有两个：

```text
所有文档输入 → CanonicalDocument
所有答题结果 → ResultRecord
```

只要这两个合同稳定，Parser、Embedding、Rerank、Solver、Verifier 都可以替换。

# 2. 四大模块

## 模块 A：文档输入与解析

### 目标

任何输入都统一成 `CanonicalDocument`。

支持：

```text
PDF
Markdown
TXT
HTML
JSON / XML
别人已经解析好的 PDF
外部 Benchmark 数据
```

### 内部拆分

```text
A1 Source Adapter
A2 Parser / Importer
A3 Normalizer
A4 Quality Audit / Repair
```

### 可替换项

```text
MinerU
PyMuPDF / PyMuPDF4LLM
Marker
OCR
VLM Parser
第三方已解析文本
```

### 统一后的“格式”是什么

这里的“统一格式”不是强制保存成某一种外部文件，而是统一成 FinDocQA 自己的 Python 数据结构：`CanonicalDocument`。

```text
CanonicalDocument
└─ pages
   └─ CanonicalPage
      ├─ text
      ├─ blocks
      ├─ tables
      ├─ formulas
      ├─ figures
      └─ lineage / quality flags
```

也就是说：PDF、Markdown、TXT、HTML、JSON 最终都先转换成同一种内部对象；后续 Retrieval / Solver 不再关心原始文件是什么格式。

### 重点改造

1. 新增统一 `CanonicalDocument / Page / Block / Table / Formula / Figure` 合同；
2. MinerU 输出先适配成 CanonicalDocument；
3. Markdown / TXT / HTML / JSON 走不同 Adapter，但最终输出一致；
4. 把表格结构解析从 Evidence 层逐步下沉到 Document Structure 层；
5. 保留现有 Parser Quality Audit；
6. 增加 OCR/VLM 第三路 fallback 的接口，但第一阶段不一定实现具体模型。

### 第一阶段不做

- 不更换 MinerU 主 Parser；
- 不马上重跑全部 190 PDF；
- 不引入重型 OCR/VLM；
- 不删除当前 page markdown / MinerU JSON。

## 模块 B：检索与证据

### 目标

统一接口：

```text
Question + CanonicalDocument Store
→ Document Candidates
→ Evidence Candidates
```

### 内部拆分

```text
B1 Document Scope
B2 Document Retrieval
B3 Page / Block Retrieval
B4 Rerank
B5 Evidence Assembly
B6 Context Compression
```

### 可替换项

```text
关键词 / BM25
Embedding
Hybrid Retrieval
Document Reranker
Cross-Encoder Reranker
Table-aware Retrieval
Formula-aware Retrieval
Visual Retrieval
```

### 重点改造

1. Document Retrieval 和 Evidence Retrieval 分开；
2. Retriever 只读取 CanonicalDocument，不直接读 MinerU 特有结构；
3. Embedding / Rerank 都通过统一接口接入；
4. 现有 lexical / structure-aware retrieval 作为第一套默认实现；
5. 后续加入 Embedding 时不改 Solver；
6. 后续加入 Rerank 时不改 Evidence / Solver 数据合同。

### Embedding / Rerank 当前策略

当前默认检索仍然**不启用 Embedding / Rerank**，但本地已经有一套经过健康检查的 SiliconFlow 备用能力：

```text
Embedding: Qwen/Qwen3-Embedding-8B
Rerank:    Qwen/Qwen3-Reranker-8B
状态:      本地 probe PASS，默认关闭
密钥:      .env.retrieval.local（Git ignore，仅本地）
```

已经新增可选 `SiliconFlowEmbeddingClient / SiliconFlowEvidenceReranker`，只有显式调用时才访问 API，不改变当前生产默认检索。

当前还补齐了：

```text
CanonicalEmbeddingIndex        显式构建页级向量索引，必须指定 max_pages
EmbeddingEvidenceRetriever     基于余弦相似度召回
ReciprocalRankFusionRetriever  Lexical / Embedding / 其他召回的 RRF 融合
EvidenceReranker               融合后可选精排
```

2 页合成文档真实 API 集成已验证：`Embedding → RRF Hybrid → Qwen3-Reranker` PASS；正式生产默认仍未切换。

后续仍支持两种接法：

```text
本地模型
Embedding Model / Cross-Encoder Reranker
→ 本机加载并推理

API 模型
Embedding API / Rerank API
→ 远程调用
```

两种方式都只实现统一的 `DocumentRetriever / EvidenceReranker` 接口，不改后面的 Evidence / Solver / Verifier。

什么时候真正引入模型，由 E2 Retrieval Benchmark 决定；先证明现有 lexical 基线，再用 Embedding / Rerank 做 A/B 对比。

### 2026-07-27 第一轮检索基准结论

已经用一组**本地私有、逐题证据闭环的确定性 Gold**完成第一轮同源对比。私有题号、答案与原始比赛细节不进入公开仓库，公开文档只保留能力结论。

结论不是“直接把向量模型切成默认”，而是：

```text
固定候选范围内：
Lexical              召回已很强，但排序能力一般
Embedding            排序能力较强，但多文档完整召回仍可能漏文档
Hybrid RRF           文档覆盖最好，但会有双路重复页拥挤
Hybrid + Rerank      当前小样本综合最好
```

本轮同时修复了三个通用问题：

```text
长页证据窗口：最早命中 → 最高密度语义窗口
Embedding / Rerank：增加单页 / 单候选字符上限，避免无界 API 请求
Rerank Query：题干 + 选项共同参与，避免多选题关键信息只在选项中
```

当前仍**不切换生产默认**。原因：

1. Gold 规模仍小，只能用于方向判断；
2. Rerank 有明显额外延迟与 API 成本；
3. 全语料评测显示，真正的前置瓶颈已经转移到 `B1 Document Scope`：很多跨文档题不是页级检索失败，而是候选文档阶段没有把所有必需文档找全。

因此下一优先级调整为：

```text
B1 Document Scope 多文档覆盖
→ B2/B3 Retrieval 保持当前可插拔链路
→ 再扩大 Gold 复测 Hybrid + Rerank
→ 最后决定是否切生产默认
```

Document Scope 当前重点不是单纯增大 `top_k`，而是建立可审计的文档身份与多槽位覆盖：

```text
题目中的公司 / 产品 / 法规 / 研究主题
→ 文档身份别名
→ 多个候选槽位
→ 每个槽位至少保留一个高置信文档
→ 再进入页 / 块级 Evidence Retrieval
```

#### B1 Document Scope 第一轮收口

2026-07-27 已完成第一轮多文档覆盖改造，仍保持零 Provider 调用。核心改动：

```text
显式文档引用规范化
+ 公司 / 产品身份别名
+ 选项 / 子命题 claim_fragment 槽位
+ 研报 claim 的正文主题 n-gram 低权重覆盖
→ coverage-aware Document Scope
```

同一套 masked 文档范围基准上：

```text
AllRequiredRecall@5   0.71 → 0.83
AllRequiredRecall@3   0.43 → 0.58
MRR                   0.863 → 0.913
Top5 未完整覆盖题数    29 → 17
```

按领域看，财报维持 1.00、保险维持 0.95；金融合同与研报的多文档覆盖有明显改善，监管小幅改善。开发用私有 Gold 的 Document Scope 仍保持全部通过。

这里的关键经验是：

```text
不要只把整道题压成一个查询
→ 强主题会淹没第二份文档

应先保留：
整题主排序
+ 明确文档身份
+ 子命题 / 选项覆盖槽位
→ 再合并候选文档
```

下一步进入 Scope → Retrieval 联合 E2，验证候选文档覆盖改善是否真正传导到 Evidence Recall，而不是只停留在文档层指标。

#### B2/B3 Canonical Retrieval 联合 E2 收口

2026-07-27 已完成 `Document Scope → Canonical Retrieval → Prompt Evidence Compaction` 的正式候选链验证。这里不是 benchmark 手工注入文档范围，而是由 `PipelineFactory` 显式选择 `canonical_lexical`，再通过通用 `ScopeAwareEvidenceRetriever` 接入现有 Scope 与审计合同。

第一轮联合 E2 的关键结论是：旧检索链即使直接给出正确文档，主要证据损失仍然存在；因此瓶颈已经从 B1 明确转移到 B3 页 / 块级检索。替换为 Canonical Lexical 后，同一小型确定性 Gold 上的证据召回显著改善。

```text
旧 Scope + Lexical Hybrid
→ Evidence Page Group Recall 约 0.64
→ Evidence Anchor Recall     约 0.50

Scope + Canonical Lexical + Prompt Compaction
→ Complete Document Recall   1.00
→ Evidence Page Group Recall 1.00
→ Evidence Anchor Recall     1.00
```

当前最小充分配置不是立即引入 Embedding / Rerank，而是：

```text
Document Scope
→ Canonical Lexical：每文档 Top5
→ Prompt Evidence Compaction：最多 20 条
```

这说明在当前阶段，先修正文档边界、页级证据召回和候选覆盖，比直接增加模型层更划算。

为避免 CanonicalDocument 只覆盖部分历史语料，正式候选链使用有序 Document Store：

```text
Raw MinerU                  优先，保留最丰富结构
→ adapted page_XXXX.md      缺 raw 文档时兜底
→ PyMuPDF 已适配目录        再兜底
→ CanonicalDocument
```

100 题零 API shadow readiness：

```text
questions                    100
retrieval exceptions           0
zero-evidence                  0
missing requested doc events   0
AnyRequired retrieved         0.99
AllRequired retrieved         0.83
平均检索延迟                  约 0.53s
```

五个领域均可以通过同一 Canonical Retriever 运行；其中监管历史后补文档通过 adapted-page fallback 接入，不需要监管 qid/doc 特判。

当前生产默认仍保持 `lexical_hybrid`，`canonical_lexical` 作为显式 shadow 候选。下一门禁是扩大联合 E2 / 端到端回归后，再决定是否切换默认；不要仅凭 8 道 Gold 直接改生产默认。

## 模块 C：答题与验证

### 目标

输入已经是标准 Evidence，专注“会不会答”。

### 内部拆分

```text
C1 Query Understanding
C2 Solver Router
C3 Deterministic Calculation
C4 LLM Reasoning
C5 Claim Atomization
C6 Evidence Binding / Verification
C7 Recovery Policy
```

### 保留现有能力

```text
题型识别
多选判断
计算题 Python 复算
跨文档比较
Claim SUPPORT / REFUTE / UNRESOLVED
主体 / 指标 / 时间 / 数值 / 单位 / 条件绑定
Failure 分类
有界补搜 / 重绑 / 重算
```

### 重点改造

1. 删除核心逻辑中的 qid / dataset 特例；
2. Solver 不感知比赛 CSV；
3. Verification 只认 Evidence + Claim；
4. Recovery 可以调用 B 模块补搜，也可以调用 A4 请求 Parser 修复；
5. 计算优先确定性 Python，不依赖 LLM 心算。

### 当前实施状态（2026-07-26）

现有 `Solver / Verifier` 接口本身已较通用，因此暂不重写；先处理答案基数与输出命名耦合：

```text
Question
→ question_answer_slot_count()
→ Solver / Verifier
→ answer_values
```

历史 `submission_slot_count / submission_slot_contracts` 暂时只作为兼容来源，新模块不再直接依赖这些名字。生产 workflow 尚未强制切换，避免一次性大改。

# 6. 改造完成后应该达到的效果

### 换输入，不改后面

```text
PDF ─────────┐
Markdown ────┤
HTML ────────┤
```
