# FinDocQA 模块化改造计划

> 目标：把当前“比赛答题流水线”改造成“可替换模块 + 统一数据合同 + 分层评测”的通用金融长文档 QA 框架。
>
> 本文定义改造顺序与验收标准，并作为正式长期路线图。2026-07-26 已开始按此路线实施：Phase 0～3 的基础合同、shadow 检索接口与四级评测代码已落地；现有生产 Retrieval / Solver 默认行为暂未切换。

---

## 1. 最终目标结构

```text
                FinDocQA
                   │
        ┌──────────┴──────────┐
        │                     │
   文档生产链             问答消费链
        │                     │
各种输入                  Question
PDF/MD/TXT/HTML/JSON          ↓
已解析文档/外部数据集      题目理解
        ↓                     ↓
Source Adapter             文档范围
        ↓                     ↓
Parser / Importer          文档召回
        ↓                     ↓
Normalizer                证据检索
        ↓                     ↓
Quality / Repair          Rerank/去重/压缩
        ↓                     ↓
CanonicalDocument          Solver
        │                     ↓
        └──────────────→ Claim验证
                              ↓
                           Recovery
                              ↓
                         ResultRecord
                              ↓
                         Output Adapter
```

最核心的边界只有两个：

```text
所有文档输入 → CanonicalDocument
所有答题结果 → ResultRecord
```

只要这两个合同稳定，Parser、Embedding、Rerank、Solver、Verifier 都可以替换。

# 2. 四大模块

## 模块 A：文档输入与解析

### 目标

任何输入都统一成 `CanonicalDocument`。

支持：

```text
PDF
Markdown
TXT
HTML
JSON / XML
别人已经解析好的 PDF
外部 Benchmark 数据
```

### 内部拆分

```text
A1 Source Adapter
A2 Parser / Importer
A3 Normalizer
A4 Quality Audit / Repair
```

### 可替换项

```text
MinerU
PyMuPDF / PyMuPDF4LLM
Marker
OCR
VLM Parser
第三方已解析文本
```

### 统一后的“格式”是什么

这里的“统一格式”不是强制保存成某一种外部文件，而是统一成 FinDocQA 自己的 Python 数据结构：`CanonicalDocument`。

```text
CanonicalDocument
└─ pages
   └─ CanonicalPage
      ├─ text
      ├─ blocks
      ├─ tables
      ├─ formulas
      ├─ figures
      └─ lineage / quality flags
```

也就是说：PDF、Markdown、TXT、HTML、JSON 最终都先转换成同一种内部对象；后续 Retrieval / Solver 不再关心原始文件是什么格式。

### 重点改造

1. 新增统一 `CanonicalDocument / Page / Block / Table / Formula / Figure` 合同；
2. MinerU 输出先适配成 CanonicalDocument；
3. Markdown / TXT / HTML / JSON 走不同 Adapter，但最终输出一致；
4. 把表格结构解析从 Evidence 层逐步下沉到 Document Structure 层；
5. 保留现有 Parser Quality Audit；
6. 增加 OCR/VLM 第三路 fallback 的接口，但第一阶段不一定实现具体模型。

### 第一阶段不做

- 不更换 MinerU 主 Parser；
- 不马上重跑全部 190 PDF；
- 不引入重型 OCR/VLM；
- 不删除当前 page markdown / MinerU JSON。

## 模块 B：检索与证据

### 目标

统一接口：

```text
Question + CanonicalDocument Store
→ Document Candidates
→ Evidence Candidates
```

### 内部拆分

```text
B1 Document Scope
B2 Document Retrieval
B3 Page / Block Retrieval
B4 Rerank
B5 Evidence Assembly
B6 Context Compression
```

### 可替换项

```text
关键词 / BM25
Embedding
Hybrid Retrieval
Document Reranker
Cross-Encoder Reranker
Table-aware Retrieval
Formula-aware Retrieval
Visual Retrieval
```

### 重点改造

1. Document Retrieval 和 Evidence Retrieval 分开；
2. Retriever 只读取 CanonicalDocument，不直接读 MinerU 特有结构；
3. Embedding / Rerank 都通过统一接口接入；
4. 现有 lexical / structure-aware retrieval 作为第一套默认实现；
5. 后续加入 Embedding 时不改 Solver；
6. 后续加入 Rerank 时不改 Evidence / Solver 数据合同。

### Embedding / Rerank 当前策略

当前默认检索仍然**不启用 Embedding / Rerank**，但本地已经有一套经过健康检查的 SiliconFlow 备用能力：

```text
Embedding: Qwen/Qwen3-Embedding-8B
Rerank:    Qwen/Qwen3-Reranker-8B
状态:      本地 probe PASS，默认关闭
密钥:      .env.retrieval.local（Git ignore，仅本地）
```

已经新增可选 `SiliconFlowEmbeddingClient / SiliconFlowEvidenceReranker`，只有显式调用时才访问 API，不改变当前生产默认检索。

后续仍支持两种接法：

```text
本地模型
Embedding Model / Cross-Encoder Reranker
→ 本机加载并推理

API 模型
Embedding API / Rerank API
→ 远程调用
```

两种方式都只实现统一的 `DocumentRetriever / EvidenceReranker` 接口，不改后面的 Evidence / Solver / Verifier。

什么时候真正引入模型，由 E2 Retrieval Benchmark 决定；先证明现有 lexical 基线，再用 Embedding / Rerank 做 A/B 对比。

---

## 模块 C：答题与验证

### 目标

输入已经是标准 Evidence，专注“会不会答”。

### 内部拆分

```text
C1 Query Understanding
C2 Solver Router
C3 Deterministic Calculation
C4 LLM Reasoning
C5 Claim Atomization
C6 Evidence Binding / Verification
C7 Recovery Policy
```

### 保留现有能力

```text
题型识别
多选判断
计算题 Python 复算
跨文档比较
Claim SUPPORT / REFUTE / UNRESOLVED
主体 / 指标 / 时间 / 数值 / 单位 / 条件绑定
Failure 分类
有界补搜 / 重绑 / 重算
```

### 重点改造

1. 删除核心逻辑中的 qid / dataset 特例；
2. Solver 不感知比赛 CSV；
3. Verification 只认 Evidence + Claim；
4. Recovery 可以调用 B 模块补搜，也可以调用 A4 请求 Parser 修复；
5. 计算优先确定性 Python，不依赖 LLM 心算。

### 当前实施状态（2026-07-26）

现有 `Solver / Verifier` 接口本身已较通用，因此暂不重写；先处理答案基数与输出命名耦合：

```text
Question
→ question_answer_slot_count()
→ Solver / Verifier
→ answer_values
```

历史 `submission_slot_count / submission_slot_contracts` 暂时只作为兼容来源，新模块不再直接依赖这些名字。生产 workflow 尚未强制切换，避免一次性大改。

---

## 模块 D：输出与评测

### D1 输出

核心输出统一为：

```text
ResultRecord
├─ answer
├─ evidence
├─ verification
├─ lineage
├─ reasoning_summary
├─ cost
└─ failure_state
```

外层再转换：

```text
JSON
Markdown
API Response
Benchmark Prediction
Legacy Competition CSV
```

### 重点改造

把当前核心中的：

```text
submission_slot_count
submission_slot_contracts
submission_answers
submission_mode
submission_template
```

逐步迁移到 `Output Adapter / Legacy Competition Adapter`。

多值答案能力可以保留，但改成通用：

```text
answer_values / answer_slots
```

而不是 `submission_*`。

### 当前实施状态（2026-07-26）

已新增：

```text
PipelineResult
→ ResultRecord
   ├─ primary_answer
   ├─ answer_values
   ├─ reasoning
   ├─ token/cost fields
   ├─ error
   └─ metadata
→ OutputAdapter
```

第一版已经提供通用 `JSON / JSONL` Writer；旧 Competition CSV Writer 暂时原样保留，后续作为 Legacy Adapter 迁移。`PipelineResult` 新增 `answer_values`，同时保留 `submission_answers` 兼容旧流程。

# 3. 四级评测

以后每个模块都有自己的成绩，不再只看最终答案。

## E1 文档解析评测

回答：

> 文档读对了吗？

测：

```text
文本覆盖
页码对齐
阅读顺序
表格结构
表头 / 单元格
公式
单位
扫描页
图表
来源血缘
```

第一版目标：50 页 Parser Gold。

来源建议：

```text
20页 自有金融 PDF
15页 FinanceBench
15页 MMLongBench-Doc
```

---

## E2 检索 / 证据评测

回答：

> 正确内容找到了吗？

测：

```text
Document Recall@K
Page Recall@K
Evidence Recall / Precision
Cross-document Complete Recall
MRR / nDCG
Claim Evidence Coverage
```

---

回答：

False Accept
False Reject
Recovery Decision Accuracy

# 4. 具体实施顺序

## Phase 0：冻结现状

目的：保证改造不是“边重构边丢能力”。

执行：

- 记录当前主目录、核心模块、现有测试；
- 保留旧输入与旧 workflow；
- 不删除比赛兼容能力；
- 新架构先采用 Adapter 包装旧能力。

验收：

```text
旧流程仍可运行
旧数据不删除
无真实 API 调用
```

---

## Phase 1：建立 Canonical Document 合同

这是第一优先级。

新建建议：

```text
src/document/
├─ contracts.py
├─ adapters/
├─ parsers/
├─ normalize/
└─ quality/
```

先定义：

```text
RawDocumentSource
CanonicalDocument
CanonicalPage
CanonicalBlock
CanonicalTable
CanonicalFormula
CanonicalFigure
SourceLineage
```

然后做：

```text
现有 MinerU 数据
→ MinerU Adapter
→ CanonicalDocument
```

验收：

- 不改现有答案逻辑；
- 一份现有文档能同时从旧格式和 CanonicalDocument 读取；
- doc/page/table/formula lineage 一致；
- 单元测试通过。

---

## Phase 2：把 Retrieval 改成只认 CanonicalDocument

先不加 Embedding。

执行：

```text
现有 lexical / structure retrieval
→ 包一层统一 Retriever Interface
→ 数据源切到 CanonicalDocument
```

目标接口：

```text
DocumentRetriever
EvidenceRetriever
Reranker
```

验收：

- 默认实现仍用现有检索；
- 新旧检索结果在基准样本上基本一致；
- Retriever 不读取 MinerU-specific 文件字段。

---

## Phase 3：建立 E1 / E2 / E3 / E4 评测框架

目录建议：

```text
src/evaluation/
├─ parser_eval/
├─ retrieval_eval/
├─ reasoning_eval/
└─ end_to_end/
```

执行顺序：

```text
E4 现有 Gold
→ E1 Parser 50页
→ E2 Evidence Gold
→ E3 Calculation / Claim Gold
```

验收：

一个版本报告至少能输出：

```text
Parser Score
Retrieval Score
Reasoning Score
End-to-End Score
```

---

## Phase 4：加入第一个外部 Adapter

优先：FinanceBench。

流程：

```text
FinanceBench PDF
→ Source Adapter
→ CanonicalDocument
→ FinDocQA
→ 与官方 answer/evidence page 比较
```

验收：

- 不修改 Retriever / Solver 来适配 FinanceBench；
- dataset-specific 代码只在 Adapter；
- 能同时得到 E1/E2/E4 指标。

---

## Phase 5：Embedding + Rerank 可插拔

这时候再升级检索。

新增实现：

```text
LexicalRetriever
EmbeddingRetriever
HybridRetriever
Reranker
```

比较：

```text
Baseline
vs Embedding
vs Hybrid
vs Hybrid + Rerank
```

主要看 E2，不先看单题答案。

只有 E2 明显改善且 E4 不退化，才进入默认链。

---

## Phase 6：拆除比赛核心耦合

当新合同稳定后再动这一块。

执行：

```text
submission_* 从 Question / Solver / Workflow 逐步迁出
→ AnswerValue / ResultRecord
→ LegacyCompetitionOutputAdapter
```

注意：不是直接删除旧能力，而是先兼容，再迁移。

验收：

- 核心 workflow 不知道比赛 CSV；
- 比赛格式仍可通过兼容 Adapter 导出；
- 普通 JSON/API/Benchmark 不经过比赛逻辑。

---

# 5. 暂时不做的事情

当前不要同时开太多战线：

```text
不马上引入完整 Agent 框架
不马上换掉 MinerU
不马上引入多个 Embedding 模型
不马上接所有公开数据集
不重写所有 Solver
不删除比赛兼容代码
```

当前核心顺序：

```text
CanonicalDocument
→ Retrieval Interface
→ 四级评测
→ FinanceBench Adapter
→ Embedding / Rerank
→ 清理 submission 耦合
```

# 7. 第一轮真正执行的范围

规划确认后，第一轮只做：

```text
Phase 0 + Phase 1
```

也就是：

1. 冻结当前能力；
2. 建 `src/document/`；
3. 定义 CanonicalDocument；
4. 写 MinerU Adapter；
5. 用少量现有文档验证；
6. 不改 Retrieval / Solver 默认行为；
7. 不调用真实模型 API。

这一轮通过后，再进入 Phase 2。
